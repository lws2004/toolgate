## 1. A-1：响应解包约定缺失（P1）

### 1.1 现象

本机两种判定服务的响应形状不同：

| 服务 | 端点 | 响应形状 |
|---|---|---|
| 本机 startlux-decide | `POST /v1/systemone` | `{answers: {qid: {...}}, usage: {...}, model: "..."}`——**无 `ok` / `result` 包装** |
| 本机 typed-decide 网关 | `POST /v1/decide/{noul,choice,score,batch}` | `{ok: true, result: {...}, latency_ms: N}`——字段在 `result` 内层 |

若实现者按「统一响应形状」的直觉写解析（或者反过来，按某一端的形状写死），接到
另一端就会出错。

### 1.2 坑有多深

**按顶层直接取 `value` / `probability` 只会拿到空对象**——typed-decide 的实测
记录明确记了这个坑（「本次即因此白跑一轮」）。这不是理论风险：包装层看起来像
「多此一举」，实现者很容易直接按顶层取字段；而**空对象不会报错**，只会让概率
静默变成缺失值——这类故障没有异常、没有日志，靠看返回值很难发现。

### 1.3 补齐

写明**适配器按各自协议形状解析，不假设统一包装**；遇到带 `ok` / `result` 的形状
**必须取 `result` 内层**，并引用 typed-decide 踩过的坑。另写明 `latency_ms` 在
台账命中时为 0（度量的是实际推理耗时，不是端到端延迟）。

**解包与形状归一是两件事**：解包只负责取到该协议的结果字段，之后仍按 §3.10 转成
§3.2 的槽位形状。

### 1.4 落点

18-deployment.md §18.1：新增「响应解包：按各自协议形状解析，不假设统一包装」小节；
95-references.md E.10：新增「对照：本机 typed-decide 网关的判定接口」小节（端点表、
三层包装、踩坑原文、幂等台账、三原语）。

## 2. A-2：远程判定源缺幂等键口径（P1）

### 2.1 现象

§18.1 的数据边界只约束 loopback（远程要显式 `allow_remote: true` 并告警，第一期
不实现远程来源）。**但没有写「远程判定源必须带幂等键」**。

同一判定重复发出，在本机链路没有任何代价（不计费、无副作用），所以这条缺失
**不会以故障形式暴露**——它只会在接云端时以账单形式暴露。

### 2.2 补齐

**每一次判定请求都必须带幂等键**，键从 turn 上下文派生：§13.4 的
`_meta.toolgate/turn` 的 `turn_id` + 请求指纹（state 与问题的哈希）。同一判定在
同一 turn 内重试用同一个键，**跨 turn 不复用**（台账不跨 turn，避免把上一轮的判定
当成这一轮的答案）。

参照物是本机 typed-decide 的幂等台账：按
`sha256(primitive + model + state + question + 选项)` 落盘，同一输入永远同一决策，
命中时零上游调用、延迟降到 0ms。

### 2.3 落点

18-deployment.md §18.1「数据边界」段之后补「远程判定源必须带幂等键」。

## 3. A-3：方案 B 的协议载体未在正文点明（P2）

### 3.1 现象

§13.4 的方案 B（turn 级聚合判定）一直在说「把同一 turn 内的多个判定合成一次 d1
调用」，但没说协议侧这件事**已经现成**。读的人会以为要设计一个新协议或新的调用
形态。

### 3.2 补齐

- **systemone 原生就是一次请求读出多个命名问题的概率**：toolgate 已实测（§18.1），
  一次请求九问、一次前向读出全部概率——这正是 §5.1 的九问分解能一次调用问完的
  原因；
- **网关侧还有同构的 batch 端点**：`POST /v1/decide/batch` 入参
  `{state, questions: {qid: {type, instructions, criteria}}}`，出参
  `{qid: 与单问同构的结果}`。

所以方案 B 要做的只有一件事：**在 turn 内把多个工具的判定问题合并成一次调用**，
问题合并、结果按 qid 回填。协议侧不新增，适配器侧不新增形状。

**聚合状态的边界不变**：只在 turn 内存在、可随时丢弃（§22.5），不得跨 turn 复用
（否则 §21.2 的「无隐藏状态」被破坏）。方案 B 的难点从来不是协议，是 turn 内的
聚合与丢弃。

### 3.3 落点

11-runtime.md §13.4「实现阶段的落点」段之后补一段（协议载体 + 要做的事 + 状态边界）。

## 4. 三处对齐的共同性质

三处都**不改对外契约**：A-1 是解析约定，A-2 是请求附加字段，A-3 是既有协议的使用
方式。它们都能在不动 §3.2 槽位契约、不动 §4.4b 告知协议、不动工具数量的前提下
落地，所以不需要用户额外拍板。

## 5. A-4：槽位契约加问题类型维度（**已评估，不采纳**，2026-11-09）

### 5.1 被评估的方案

给 §3.2 的 decide 契约加**问题类型维度**（`noul` / `choice` / `score`），与 TypeSafe
三原语对齐：`questions` 从字符串数组变成带 `type` / `criteria` 的对象数组，输出按
类型分支（noul 给 `probability`、choice 给 `distribution`、score 给 `level` +
`distribution`）。

动机是判定服务侧的形状比契约宽（附件 E.10），差距看起来可以用一个类型维度填平。

### 5.2 否决理由

**1. 契约会变大且变成联合类型，而扩展的是没有调用方的槽位。**

`questions` 变成带类型字段的对象数组后，校验、消费、门控都要按类型分支——每一处
消费 decide 输出的地方都要先判类型。而**现在在用的只有 decide 的二元形状**，其余四个
槽位（classify / rerank / summarize / vision）都还没有真实调用方。为没有调用方的
形状引入分支，是拿确定的复杂度换不确定的收益。

**2. classify 的逐标签分布、rerank 的逐候选分数，本来就是各自槽位契约自己的事。**

§3.2 里 classify 就是 `{text, labels}` → `{scores}`，rerank 就是
`{query, documents}` → `{results}`——它们的输出形状是各自契约定义的，不需要 decide
契约长出类型维度来承载。**五个槽位本身就是五种答案形状，正是三原语的映射目标**：

| 槽位 | 对应的原语 |
|---|---|
| classify | choice 的 `distribution`（逐标签分布） |
| decide | noul 的 `probability`（逐问题概率） |
| rerank | 按候选的分布 |
| summarize / vision | 不是判定原语 |

让 decide 一个槽位承担三种问题形状，是把「每槽位各自的形状」揉进一个联合类型——
正好与三原语的映射关系相反。

**3. §18.1 的「协议选择原则」已经表达了正确的对齐方式。**

上一轮写进正文的协议选择原则（§18.1）说的就是**每个槽位各自映射到合适的原语**，
而不是让一个槽位承担三种问题形状。契约层要加类型维度，等于在契约层重复一套
更笨的映射机制。

### 5.3 重新评估的触发条件

**将来满足以下任一条，才重开这个话题**：

1. 某个非 decide 槽位（classify / rerank）有了真实调用方，**且**它的槽位契约的输出
   形状无法由现有原语映射；
2. 某工具的判定请求确实需要有序 / 多选语义，**且**二元分解被实测证明不可靠
   （例如 severity 的二元分解在真实错误样本上判错率过高）。

两条都要求**证据**（真实调用方 / 实测判错率），不要求「预先准备好」。

### 5.4 澄清：§5.1 的九问二元分解不是将就

§5.1 现在的九问分解**不是「将就」，而是在 decide 契约保持二元形状下的最小可用
形态**。它啰嗦，但自洽：九个问题共享一次 state 读取、一次前向读出全部概率
（§18.1 的实测），且**不引入未使用的分支**——契约里没有类型维度，实现里也不该有。

### 5.5 落点

本报告第 5 节（否决记录）。**§3.2 正文未动**；§5.1 的九问分解、§3.10 的适配器
归一、§18.1 的协议选择原则三处保持原样，与本否决结论一致。
