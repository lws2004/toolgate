## 1. D-1：判定类槽位的协议选择原则缺失（P2）

### 1.1 现象

用户的问题是「decide、classify 是否应该用 systemOne 协议？其它模型做 decide /
classify 时再转为 systemOne 形状？」——这个问法把**槽位**、**协议**、**模型**
三件事混在了一起。正文里没有一条规则回答它，实现者只能各自理解：可能把 decide
写死成 systemone（那通用 LLM 就做不了 decide），也可能给所有模型都套一层
systemone 形状（多一层无意义的映射）。

### 1.2 澄清：槽位与协议是两件事

§3.0 的「架构定义槽位，不定义模型」在这里同样成立——**槽位契约与协议无关**。
§18.1 的总纲也已经写明「模型来源是部署形态，不是能力等级」。所以正确的问题不是
「decide 只能用 systemone」，而是「**能用 systemone 的模型就用它**」。

差别在**概率的性质**，不在能不能做：

| 模型类型 | 协议 | 适配器 | 概率性质 | §7.2 门控 |
|---|---|---|---|---|
| jev 类判定模型 | `systemone` | `native` | 校准概率（后端按 read-out 概率 + 校准训练得到） | 可用：直接套 0.85 / 0.60 阈值 |
| 通用 LLM | 自身协议（`openai` / `anthropic` / `responses`） | `json` | 自报值，非校准（§3.10） | 不可直接套用：走最保守档 + `UNCALIBRATED` 标注 |

### 1.3 不要把通用模型包装成 systemone 形状

三条理由：

1. **适配器的职责本就是直接归一**。§3.10 的适配器把槽位请求转成该协议的原生形状、
   再把输出转回 §3.2 槽位形状。openai 的原生形状是「prompt + JSON schema 输出
   （或 logprobs）」，不是 systemone 的「命名问题 + noul / choice / score」。强行
   先转 systemone 形状再转回槽位形状，只是多一层映射、多一处真相、多一处可能
   出错；
2. **包装不会凭空产生校准性**。systemone 的价值在于后端是按 read-out 概率加校准
   训练做的判定模型；套协议外壳不改变概率性质，对 decide 的核心价值（门控可用）
   没有帮助；
3. **要一致的是语义，不是协议形状**（见 D-3）。

### 1.4 落点

18-deployment.md §18.1：新增「协议选择原则：判定类槽位该用哪个协议」小节（澄清
表 + 模型类型对照表 + 三条理由 + 边界声明）。

## 2. D-2：非校准概率与门控阈值的关系未定义（P1）

### 2.1 现象

§7.2 的门控阈值（`p ≥ 0.85` 采用 / `0.60 ≤ p < 0.85` 标低置信 / `p < 0.60`
两视图都给）是**按校准概率标定的**——「概率 0.9 的判定，实际有九成是对的」，
只有概率经过标定，「0.85 才敢采用」才成立。

但 §3.10 允许 `json` 适配器的**非校准概率**（模型自报值）进入同一个 decide
契约。正文只写了「高风险判定只能用 `native`，或由云端复核」——**没有明确非校准
概率走门控时怎么处理**。

**标注了不等于可信**：§3.10 要求非校准概率带 `calibrated: false` 与 §4.4b 的
`UNCALIBRATED` 告知，但告知是给调用方看的，**门控是工具自己做的分支**。门控不能
因为「反正已经标注过了」就照用校准阈值——那会把一个自报值 0.95 当成有九成五把握
的判定来采用。

### 2.2 口径

1. **阈值只对校准概率标定**：非校准概率**不得直接套用 0.85 / 0.60**——那套数字的
   前提（概率经过标定）不成立；
2. **未标定协议走最保守档**：`json` 适配器产出的概率一律按「两视图都给 +
   `UNCALIBRATED` 标注」处理（fail-safe，不乐观采用），而不是按 p 值分档采用；
3. **等实测标定后再改**：某个协议在本机实测出可用的专用阈值后，再按 §15.6 的
   「判定准确率」指标（待标定）观测它，并在本机标定出专用阈值，届时才允许按档位
   采用。标定的做法可参照 §10.2b 的质量阶梯标定（§15.7 的「质量阶梯基准」条目）。

**这不是新概念**，是把 §3.10「非校准概率必须标注」这条既有规则在**门控处的
后果**写明：标注了还不够，门控也不能信它。

**与 `UNCALIBRATED` / `LOW_CONFIDENCE` 的关系**：两者正交（§4.4b 的 code 选择
规则第 5 条）。非校准概率**总是**发 `UNCALIBRATED`；是否也发 `LOW_CONFIDENCE`
取决于走哪档——保守档下两者都发（概率性质 + 不确定性），校准概率在 0.60–0.85 档
只发 `LOW_CONFIDENCE`。

### 2.3 落点

06-cost.md §7.2：新增「阈值只对校准概率成立」小节（口径三条 + 与两个 notice code
的关系）。§18.1 的协议选择原则表的「§7.2 门控」列指向该小节。

## 3. D-3：「语义一致 vs 协议形状一致」的边界未划（P2）

### 3.1 现象

「所有模型统一走 systemone 形状」这个提议背后是一个合理直觉：**统一形状 =
统一语义 = 结果可比**。但这两件事不等价，而且**划清边界有实际的防错价值**——
不划边界，后来人很可能顺手加一层「协议统一层」，让所有请求先转成 systemone
形状。

### 3.2 边界

要一致的是**语义**，不是协议形状：同一个 decide 请求无论走哪个协议，问的都是同样
的语义问题（§5.1 的 `has_error` / 错误种类 / `severity` / `needs_full_context`），
载体不同语义一致。**这由槽位契约（§3.2）与工具层的问题定义（§5.1）保证，不由协议
形状保证。**

§3.10 的适配器**都直接归一到 §3.2 槽位形状，不经过中间协议形状**——systemone
适配器转成命名问题、`json` 适配器转成 prompt + JSON schema，各自直接对上槽位
形状。

### 3.3 落点

18-deployment.md §18.1 协议选择原则的第 3 条理由；03-slots.md §3.10 在
「非校准概率必须标注」相邻处补一段「各协议适配器都直接归一到 §3.2 槽位形状，
不经过中间协议形状」。

## 5. 遗留

1. **通用 LLM 的 decide 门控阈值没有专用值**：本轮定的口径是「未标定协议一律走
   最保守档」。要让它按档位采用，需要按 §15.6 的「判定准确率」指标（待标定）
   在本机实测某个通用协议的自报概率与实际正确率的关系，定出专用阈值。这是标定
   工作，不是架构空白。
2. **`json` 适配器在 decide 上的实际表现未实测**：本轮的口径基于「自报概率非
   校准」这一既有判断（§3.10）。它在真实调用里的分布如何，等实现接线后按
   §15.6 观测。
3. **systemone 的 `choice` / `score` 类型仍未映射**：本轮只涉及 `noul`，走
   `choice` 的 classify 映射与 `none_probability` 的降级语义待定（§18.1 能力表
   标「受限」）。
4. **本机 Rust 工具链与仓库 MSRV 已是最新**（rustc 1.99.1、仓库 1.89），本轮无依赖
   变动，附件 E.8 的数字未变。
