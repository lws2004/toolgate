# toolgate 架构复审（2026-11-07）

> 复审对象：`docs/architecture.md`（工作区未提交版本，3193 行）

## 0. 结论摘要

这份架构的强项已经很清楚：三形态成本模型（F1/F2/F3）把「省 token」的账算清了，槽位抽象把「不绑定模型」落到了可替换的契约上，隔离四档与回退链把「数据不出本地」从口号变成了配置。这些都是上一轮迭代的实质成果。

残余问题不在「工具设计」，而在**从「单次调用」升级为「常驻服务 + 多客户端 + 可编排」时缺的三类横切契约**：

| 类别 | 缺什么 | 后果 |
|---|---|---|
| 执行模型 | 并发、取消、task 生命周期、多客户端隔离 | PTC 并发退化为串行；多客户端可互相 kill 任务 |
| 数据流顺序 | 脱敏、落盘、快照、缓存四者的先后 | 敏感内容以明文落在磁盘上，绕过了隔离 |
| 契约边界 | 错误码、配置、版本兼容、模型可见通道 | 程序无法稳定判断错误；升级破坏 v1 行为 |

按严重度统计：**P0 5 条、P1 8 条、P2 15 条、P3 5 条**。

## 2. P0：先定再写代码（5 条）

### P0-1 隔离规则只覆盖「输入路径」，覆盖不了「命令输出」

**位置**：§8.5（配置的 rules 只有 path glob）、§8.2（bash 最强 understand）、§17.2

**现象**：配置规则按路径匹配，但 bash 的入参是 `binary + args`，输出可以是任意文件内容。`bash {binary:"cat", args:[".env"]}` 不会命中 `**/.env* → none`；`search` 命中跨多个文件，也无法按输出路径逐条套规则。§8.2 说 bash 的 understand 档靠 decide 判定，但 §8.5 的规则表里没有「内容级」这一层。

**为什么是 P0**：bash 是收益最大、也是数据暴露面最大的工具。隔离的核心承诺在它身上不成立，等于把最贵的门留在了最该锁的位置。

**建议**：
1. 增加「输出内容级策略」层：命令输出先过机械脱敏（§8.10 的正则 + 熵检测），命中则按 `fallback_chain` 降级；
2. 对 bash/search 增加 `isolation.content_rules`（类型：密钥模式 / 敏感路径名出现在输出里 / 高熵串），与路径规则取交集；
3. 把「路径规则覆盖不了输出」写进 §8.2 的边界，不要留给实现猜。

**验收判据**：给定 `cat .env` 与 `**/.env* → none`，返回值不包含任何 `.env` 内容，且告知「命中输出内容级规则」。

### P0-2 敏感内容「先落盘、后脱敏」的顺序漏洞

**位置**：§8.10（「脱敏位置在工具返回之前」）、§9.3（流水线：执行 → 截断 + 落盘 → 模型读落盘文件 → 摘要）、§20（快照）

**现象**：落盘发生在「返回之前」，所以 `/tmp/toolgate-spill/` 里的 bash 输出是**未脱敏原文**；`.toolgate/snapshots/` 里的旧内容是**未脱敏原文**。即使 read 回读时再脱敏，磁盘上的明文已经存在，同机其他用户或进程可读。

**为什么是 P0**：这是「数据隔离」架构里唯一会被绕过的一环，而且是静默的——调用方看到的是脱敏后的返回，不知道磁盘上还有一份原文。

**建议**：定义统一的流水线顺序，并在 §9.3 与 §8.10 各写一次（现在两处各说各的）：

```text
执行 → 截断（保尾部）→ 机械脱敏 → 落盘（脱敏后的副本，权限 0600）
     → 本地模型读「落盘副本」或内存原文做摘要 → 摘要再做一次脱敏 → 返回
```

两条补充：
- 快照必须保存**原始字节**（见 P1-4），但目录权限 0700、文件 0600，并明确「快照不脱敏」的边界——因为回滚要保真；
- 如果「快照不脱敏」不可接受，替代方案是快照加密落盘，但这会把密钥管理引入工具层，成本更高，建议先用权限边界。

**验收判据**：含 AWS key 的 bash 输出，其 spill 文件内容中该 key 已替换为 `[REDACTED:AWS_KEY]`，文件权限 0600；快照目录权限 0700。

### P0-3 「meta 不进模型上下文」是客户端依赖，却承载了可信度告知

**位置**：§7.3（降级静默，meta 标注）、§16.3 对策二（耗时放 structuredContent）、§7.2 与 §13.3（confidence / slm_status 字段）

**现象**：文档多处把耗时、置信度、`slm_status`、降级原因放进 `structuredContent`，默认「模型看不到」。这在 DSH 上成立（已核实其 `render()` 只投影 `content` 文本），但这是**客户端行为，不是 MCP 协议保证**。pi、Claude Code 等客户端可能把整个 result 序列化进上下文。

**为什么是 P0**：§8.7 说「不告知等于欺骗」——隔离回退要显式告知；但 §7.3 的能力降级只放 meta。同一个原则在两个地方用了两套标准。若客户端把 meta 也喂给模型，问题消失；若客户端不喂，模型不知道摘要是降级产物，会在不该确定的地方确定。

**建议**：定义「双通道」规则并写进 §4.3：
- **模型可见通道（content 文本）**：截断、降级、低置信、隔离回退、槽位不可用——凡影响模型判断的内容必须在这里；
- **程序通道（structuredContent）**：耗时、路径、行号、字节数、错误码——供调用方做逻辑，不承担告知义务。

把 §7.3 的「降级是静默的」改为「对程序静默，对模型显式」；§7.2 的 confidence 低于 0.6 时，content 里必须带一行「本地判定置信度低，以下是判定与原文两版」。

**验收判据**：在「只渲染 content」与「渲染整个 result」两种客户端上，降级、截断、低置信三种情况的模型都能从 content 文本读到告知。

### P0-4 并发与生命周期契约缺失

**位置**：§21.2（要求并发安全）、§18.1（支持 HTTP 多客户端）、§5.5（task）、§21.7（本地 agent 并发调用）

**现象**：
- 传输层没有定义并发模型。v1 的 `McpServer::serve_stdio` 是单循环逐请求 `await`，PTC 里 `Promise.all` 的并发调用会被串行化；§21.2 只讲了「数据不被破坏」，没讲「请求怎么并发执行」；
- `task` 的 registry 是进程级全局 `HashMap`，HTTP 多客户端模式下客户端 A 可以 `kill` 客户端 B 的任务；
- task 没有回收策略：每个任务最多 4MB 输出，进程不退出就永不释放。

**为什么是 P0**：PTC 形态（F2）的核心卖点是「程序里连续调、并发调」；并发退化会让 F2 的收益直接打折。多客户端越权则是安全问题。

**建议**：新增「执行模型」章节（建议放在 §18 与 §21 之间）：
1. 并发：每请求一个 tokio task，全局并发上限（默认 = CPU 核数 × 2），超出排队并返回 `queueDepth`；
2. task 表按「会话 ID / 客户端 ID」分区，服务端从请求 `_meta` 取会话标识；无标识时按连接隔离；
3. task 生命周期：进程退出后保留 30 分钟或最多 100 条，先到先回收；task_id 用会话内单调计数器，不用时间戳（当前实现 `Instant::now().elapsed()` 几乎恒为 0，同一进程第二次 start 会覆盖前一个任务）；
4. 取消：响应 MCP `notifications/cancelled`，杀进程组（不是只杀父进程）；
5. 落盘与快照用「临时文件 + rename」原子写，否则并发读可能读到半截文件（§21.2 声称的并发安全目前没有实现支撑）。

**验收判据**：10 个并发只读调用的 P95 排队延迟 < 单次执行的 2 倍；A 客户端无法 kill B 的任务；task 退出后被回收。

### P0-5 「可重放」对副作用工具不成立

**位置**：§18.4（「每次 tools/call 的结果都是可重放的（输入确定、输出确定）」）、§16.3 对策二、§21.2

**现象**：确定性 ≠ 幂等。`write`/`edit`/`bash` 有副作用，重放会重复执行（重复 push、重复删文件、快照多一份）。§18.4 却把「可重放」当成断点续传的基石，说调用方「只要记录已完成哪些调用，就能重建状态」。

**为什么是 P0**：调用方按这句话设计 checkpoint，会在写操作上重复执行；这不是文档措辞问题，是契约错误。

**建议**：把 §18.4 改成两张表：
- **只读工具（read/search/部分 bash）**：输入确定、输出确定、可重放；
- **写工具（write/edit/bash 副作用）**：不可重放，必须由调用方的 checkpoint 保证「已执行的调用不再执行」；工具层提供 `operationId` 让调用方做幂等键（相同 operationId 的重复调用返回首次结果）。

**验收判据**：§18.4 不再出现「所有 tools/call 可重放」的表述；写工具的返回里带 `operationId`。

## 3. P1：阶段 1 前必须定（8 条）

### P1-1 错误码体系缺失

**位置**：§1.4.5、§21.2（「错误可编程判断」）

**现象**：错误只有自然语言 `fact/reason/next_steps`，程序无法稳定区分「文件不存在」「编码错误」「锚点失配」「编辑歧义」。§21.2 要求程序能判断错误，但没有可枚举的 code。

**建议**：加 `errorCode` 枚举（`PATH_NOT_FOUND` / `ENCODING_INVALID` / `ANCHOR_MISMATCH` / `EDIT_AMBIGUOUS` / `TIMEOUT` / `OUTPUT_LIMIT` / `SLOT_UNAVAILABLE` / `ISOLATION_REFUSED`），放 `structuredContent.error.code`；`next_steps` 保留人读。同时修 §1.4.5 示例与实现的三处不一致：文档三变体 vs 代码四变体（多 `Io`）、`BadArgument` 没有 `next_steps`、代码 `Failed(String)` 把事实/原因/下一步压成一个字符串（原则说「每个变体强制携带三段」但示例与实现都没有）。

### P1-2 兼容性与默认值

**位置**：§4.2（auto 默认）、§3.8（槽位一旦配置就改变返回形态）

**现象**：v1 客户端不传 `intent`，升级到 v2 后默认 `auto` 会把「原文」变成「可能摘要」——破坏性变更，而且违反 §4.3「行为可预测」的承诺。

**建议**：v2 首版默认 `raw`（保持 v1 行为），`auto` 需显式配置开启；或引入配置项 `intent.default: raw|auto`，并在 §14 路线图加「兼容性」里程碑（升级指南 + 客户端迁移）。

### P1-3 配置层没有落点

**位置**：§3.8 / §8.5 / §18.1 / §22.3 四处 YAML 片段

**现象**：有配置形态，没有：配置文件路径、加载顺序（CLI > env > 文件 > 默认）、schema 校验、热加载策略、错误处理（配置错必须 fail loud 还是静默降级）。

**建议**：新增「配置参考」附录，给一份完整示例（slots / isolation / slm / limits / snapshots / logging）；定义加载顺序与「配置错误启动即失败」；CLI 增加 `--config` / `--root` / `--log-level`。

### P1-4 快照必须是字节级

**位置**：§20.2、`write.rs` 41-47、`edit.rs` 92

**现象**：文档说快照是「旧内容 SHA-256」，代码保存的是解码后的文本。对 GBK / Shift-JIS / 有损解码文件，快照不是原始字节，回滚会破坏文件——这与 §5.6「读改写保真」的底线冲突。

**建议**：快照 API 改为 `snapshot(path, &[u8])`，哈希按原始字节；meta 记录原路径、编码、mtime、size。§20.2 明确「快照是字节副本，不是文本副本」。另外，`write` 覆盖已存在文件时若解码出现替换字符，应像 `edit` 一样拒绝写入——当前实现忽略 `had_errors` 直接覆盖，会破坏原字节。

### P1-5 模型后端与「单二进制」的矛盾

**位置**：§19.3（单二进制、无运行时依赖）vs §18.1（embedded backend: llama-cpp | mlx）

**现象**：llama.cpp 是 C++ 动态库，MLX 是 Apple 框架——embedded 模式会引入非 Rust 依赖与平台绑定，「单二进制」卖点在最需要它的部署形态上不成立。

**建议**：把发行形态拆成两类：**纯 L0 版**（单二进制，无模型）与**带 SLM 版**（主程序 + 模型后端，按平台分发）；评估 Rust 原生推理（candle）作为第三条路径；在 §19.4 代价表补这一条。同时补内存账：d1-2B + LFM3-1.7B + VL-2B + rerank-570M 同时驻留的峰值 RSS（量化前后），决定哪些槽位必须互斥。

### P1-6 文档 SSOT 违规

**位置**：`requirements-coverage.md`、`value-audit.md`、`architecture.md`

**现象**：三份文档维护同一套结论。后两份的核对时间停在「架构文档 2452 行」版本，正文已到 3193 行，且每次架构改动都要同步三处——这正是项目自己纪律里禁止的重复维护。

**建议**：`architecture.md` 作为唯一 SSOT；另外两份冻结为「历史核对档案」（顶部标注「仅记录截至 2452 行版本的核对结果，不再维护」），或合并为架构文档的附录一节。后续新增的核对结论只进 architecture。

### P1-7 实现差距表失真

**位置**：§13.1 / §13.2 / §13.3

**现象**：
1. §13.1 说「MCP 传输 完成、不变」——v1 的传输循环虽然能接收无握手的 `tools/call`，但 2026-07-28 的关键特性 per-request `_meta`（当前模型能力）与版本校验没有实现，`initialize` 分支只是遗留兼容；这项工作 §13.2 未列；
2. §13.1 说「6 个工具的 L0 层 完成」——edit 缺模式 C（patch）、read 缺单行超长落盘、search 缺超时，且 §17.2 自己承认路径根校验未实现、bash/task 的环境变量白名单只写在文档里；这些是安全差距，不只是「功能未做」；
3. §13.2 说「SLM 客户端（d1 / LFM3 / VL 三个接口）」——五槽位至少需要五个契约适配（classify/rerank/decide/summarize/vision），即使复用模型也要五套 prompt 与输出解析，工作量低估；
4. README 写「47 个测试」，实测 57。

**建议**：重写 §13 为「差距矩阵」（能力 × 现状 × 缺口 × 工作量 × 依赖），并把这四项补进去；README 的测试数改为 CI 产出的实际值。

### P1-8 §15.4 里两条「未决」现在就能定

**位置**：§15.4（auto 与能力协商的叠加顺序、并发 edit 冲突）

**建议**：
- **叠加顺序**：固定为「能力（能不能收）→ 隔离（该不该给）→ intent（想要什么）」三段串联。前一段是硬约束（不满足就降级并告知），后一段是偏好（只在允许范围内生效）。给一张四象限矩阵（内容敏感 × 上游能力）。
- **并发 edit 冲突**：读时记录 `(mtime, size, sha256)`，写前复核；不一致即拒绝，返回当前内容与 diff；不做三方合并（工具层不猜）。

把这两条从 §15.4 移到正文，§15.4 只剩「需要真实数据才能定」的项。
