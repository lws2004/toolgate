## 1. T-1：多值问题与二元槽位契约不匹配（P1）

### 1.1 现象

§5.1 的 bash 路径图里，decide 一次前向问四个问题：

```text
has_error?          概率
error_kind?         编译 / 测试 / 权限 / 网络 / 资源 / 未知
severity?           阻断 / 警告 / 噪音
needs_full_context? 是/否
```

但 §3.2 的 decide 槽位契约是**二元形状**：「每个问题一个概率」，没有类型维度——
槽位只问「这个问题的概率是多少」，不表达「从哪几个选项里选」。§3.10 的 systemone
适配器本轮也只映射 `noul`（`choice` / `score` 按形状不符处理）。

**契约与用法对不上**：图里的 `error_kind?` 与 `severity?` 是多值语义，实现者
要么发现槽位不支持、改问法（但正文没写怎么改），要么硬塞进二元形状（那
「编译 / 测试 / 权限」这六个值到底对应哪个概率？）。这是落地时必踩的空白。

### 1.2 补齐：二元分解 + 归并规则

把多值语义**分解成若干二元问题**，一次请求问完：

| 组 | 问题 | 数 |
|---|---|---|
| 是否有错 | `has_error` | 1 |
| 错误种类 | 编译 / 测试 / 权限 / 网络 / 资源，各问「是不是这类？」 | 5 |
| 严重程度 | 「阻断？」、「噪音？」 | 2 |
| 是否需要全文 | `needs_full_context` | 1 |
| | **合计** | **9** |

九问一次调用，不是九次——这正是 §13.4 方案 A 里「systemone 一次前向读出全部问题
的概率」的能力（每个问题一个独立概率，共享同一次 state 读取）。

**归并规则**：

| 字段 | 规则 |
|---|---|
| `errorKind` | `has_error` < 0.5 → `"none"`；否则取五个候选里概率最大者，最大者 < 0.5 → `"unknown"` |
| `severity` | 阻断概率 ≥ 0.5 → `"blocking"`；否则噪音概率 ≥ 0.5 → `"noise"`；否则 `"warning"` |
| `needsFullContext` | 该问题概率 ≥ 0.5 为真 |
| `failedItems` | 本轮留空（见 T-4） |

**归并规则为什么值得写进正文**：阈值 0.5 是**归并的阈值**，不是 §7.2 的**门控
阈值**（0.85 / 0.60）——两者作用不同：门控决定「采不采用这个判定」，归并决定
「这个判定落到哪个字段值」。正文不写，实现者会混用：拿 0.85 去归并 errorKind，
会让绝大多数真实错误被判成 `"none"`。

### 1.3 落点

04-tools.md §5.1：新增「L1 判定的落地口径：多值语义分解成二元问题」小节。

## 2. T-2：判定输入 state 的边界未定义（P1）

### 2.1 现象

§6.1 写明「d1 默认开启的前提是 **state 有界**——先由 L0 把候选压到 ≤2K token」，
§6.4 写「超过约 2K token 的原文不整份喂槽位模型；先做确定性召回，拼成有界窗口」。
但**bash 的判定 state 具体怎么取**（截断后的哪一段、多长）没有写。

这不是实现细节：取头部还是尾部、取多少，直接决定「错误在第 3000 行时能不能判出来」。
§9.3 已经指出「语义层需要看完整内容才能判准」与「不能把 50MB 喂给 2B 模型」的
张力，但没说 bash 这一侧怎么落。

### 2.2 补齐

**判定 state = 命令输出经 L0 双阈值截断后的最后 8000 字符**（§6.4 的 prefill
预算口径，不是整份输出）。取尾部是因为错误信息通常在末尾。

**同时写明这个窗口的代价**：错误若在被截掉的前部就判不出来，**此时的表现是概率
偏低，不是假阳性**——因为九个问题里有八个（错误种类、严重程度、是否需要全文）
在「没有错误」时都会给低概率。这条写明很重要：否则实现者看到「没判出来」会
怀疑是模型坏了，实际是窗口没覆盖到。

### 2.3 落点

04-tools.md §5.1 同一小节。

## 3. T-3：slmStatus 与 confidence 的产出规则未落（P2）

### 3.1 现象

§7.3 写明 `slmStatus` 是封闭四态（`ready` / `loading` / `unavailable` /
`degraded`）、`meta.confidence` 是本次判定的概率，**没有判定输出时为 `null`**。
但「实现怎么产出这些值」没写——结果是实现侧先返回了**硬编码的全 `unavailable`**：
字段在、契约在，值不是真实状态。

### 3.2 补齐

**`slmStatus` 的来源**：

| 状态 | 判定依据 |
|---|---|
| `unavailable` | 该槽位**未绑定**（§3.10） |
| `ready` | 已绑定且健康（首次使用校验通过，§3.11） |
| `degraded` | 已绑定但连续失败被禁用，或形状校验不符（§3.11） |
| `loading` | embedded 懒加载未就绪（§18.1）——**当前实现不产出**，因为 embedded 后端尚未实现（§19.6 可选层） |

**`meta.confidence` 的来源**：本次 L1 判定输出的概率；**多问题时取各问题概率的
最小值**（最不确定的那个决定本次结论的可信度）；没有判定输出时为 `null`。

**取最小值而不是平均值**：平均值会掩盖掉一个几乎确定的否定结论，让整体看起来比
实际更可靠——而门控（§7.2）恰恰是拿这个数做分支的，取最小值是保守方向。

**硬编码全 unavailable 这件事写成实现状态的修正说明**，不写成架构变更——契约
（封闭四态、按状态取值）从未变过。

### 3.3 落点

06-cost.md §7.3：新增「槽位状态与 confidence 的真实来源」小节。

## 4. T-4：`failedItems` 语义未定却被列入结构化输出（P2）

### 4.1 现象

§5.1 的 structured 形态写 `{exitCode, errorKind, severity, failedItems[], spillPath}`，
§9.2 也把 `failedItems` 列为 `intent=structured` 的产物。但**`failedItems` 的
语义从未定义**——它要表达「哪些具体条目失败了」，需要定位到条目级标识（测试名、
错误码、行号），这依赖命令的输出格式，跨命令没有统一的抽法。

### 4.2 补齐

**本轮留空**，并写明为什么：**语义未定义就留空，不编造**——填一个看似合理但无
定义的数组比留空更糟，调用方会以为它有含义。

这不是「功能没做完」的托词，是一条可复核的判断：要定义 `failedItems` 得先回答
「条目级标识从哪来」，那是跨命令的抽取问题（可能需要按命令类型分别处理），属
独立工作，不该在本轮的判定落地里顺手编一个。

### 4.3 落点

04-tools.md §5.1 同一小节的归并规则表与说明段。

## 5. T-5：「判定不可用」与「判定为无错」的边界（P3）

### 5.1 现象

判定不可用有多种原因（槽位未绑定、`external-protocols` feature 未开启、调用失败、
intent=raw 未触发、未达 500 token 门槛）。如果实现把它们都记成「判定结果 = 无错」，
调用方会拿到一个假的否定结论——**这比没有判定更坏**：没有判定时调用方知道自己
得自己看，有假判定时它会信。

### 5.2 补齐

明确写入：**判定不可用时工具照常工作**——按 L0 结果继续，按 §3.8 降级并按 §4.4b
发 `SLOT_UNAVAILABLE` 告知，`meta.confidence` 为 `null`。**不判错、不判类型。**

配合 T-3 的「没有判定输出时 confidence 为 `null`」——**`null` 是「没判定」与
「判定为无错」的分界**：`null` 表示没有判定输出，`p` 值（哪怕是 0.01）表示
判定确实给出了「否」。

### 5.3 落点

04-tools.md §5.1 同一小节；06-cost.md §7.3 的 confidence 来源表（`null` 的三种来源）。

5. **`meta.confidence` 取最小值的合理性未做实测标定**：九个问题里取最小值是
   保守方向，但「最小值是否过度保守」（例如某个无关问题的低概率拖低了整体）
   需要真实调用分布来评估。本轮先按保守方向定，实现稳定后再按实测复核。
6. **实现侧待收口的两处口径**（正文已定，实现跟上即可，不是契约争议）：

     判定接线还在做，窗口取法（截断后取尾部 8000 字符）需在接线时实现；
   - **500 token 触发门槛**目前只在 `intent=auto` 侧生效（实现里是
     `tokens < 500 → raw`）；`intent=summary` / `structured` 尚未按 §5.1 的口径
     加同样的门槛。两处都属于实现收口，改的是代码不是正文。
