# ADR 0003：输出治理按内容位置分治

- 状态：已采纳
- 日期：2026-11

## 背景

原始设计文档写「任何工具返回超过 2000 行 / 50KB，触发截断；完整输出
自动落盘」。

核实 pi 的实际做法：

- read 截断后**不落盘**，只给 offset 续读提示（read.js:134-151）；
- 只有 bash 落盘（output-accumulator.js:198-212）。

## 决策

按内容位置分治，不搞统一落盘：

| 工具 | 截断方向 | 落盘 |
|---|---|---|
| read | 头部 | 否 |
| search | 头部 | 是 |
| bash | 尾部 | 是 |
| task | 尾部 | 是 |

## 理由

**read 落盘是纯浪费**：文件本来就在磁盘上，复制一份到临时目录只是
多占空间，而且模型拿到指针后还得再 read 一次——不如直接给 offset。

**search 必须落盘**：检索结果不可重现。同一个 query 在不同时刻可能
返回不同集合（文件变了），所以「重跑一次」不等于「拿回同样的结果」。

**bash / task 必须落盘**：输出只存在于进程管道里，进程结束就没了。
不落盘等于永久丢失。

## 落盘命名的选择

用内容寻址（sha256 前 16 位）而非随机 hex。pi 用随机 hex
（output-files.js:16 用 randomBytes(8)），每次都是新文件。

内容寻址的代价是想按时间顺序翻日志不方便；收益是重跑同一条命令不会
让磁盘膨胀。对 agent 场景，后者更重要。
