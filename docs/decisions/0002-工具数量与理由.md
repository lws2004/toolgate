# ADR 0002：工具数量定为 6，理由是三条约束

- 状态：已采纳
- 日期：2026-11

## 背景

原始设计文档说「6 大核心厚工具」，理由是「Pi 风格的精简哲学」。

核实发现：

- pi 实际是 8 个工具（read/bash/powershell/edit/write/grep/find/ls）；
- 行业不存在工具集收敛趋势：Claude Code 46 个工具且专门设了 ToolSearch，
  Gemini CLI 约 20 个，Codex CLI 约 16 个。

所以「Pi 风格 = 极简」这个前提不成立。需要重新论证 6 这个数字。

## 决策

保持 6 个工具（read/write/edit/search/bash/task），但论证换成三条约束。

## 三条约束

> **现行表述（2026-11-07）**：正文 §4.0 已采用本 ADR 的三条（缓存前缀稳定 / 治理规则集中 / 语义边界清晰），并把「上下文预算」并入缓存前缀稳定、「智能层门槛」并入语义边界清晰。本 ADR 是原始论证，正文是现行表述。

**A. 缓存前缀稳定**：工具表在请求里，抖动即失效。工具应覆盖高频动作，
低频动作走组合而非新增工具。

**B. 治理规则集中**：每条治理规则只在一个工具里实现。这直接导致
grep + find 合并为 search（两者的超限落盘逻辑完全一样）。

**C. 语义边界清晰**：职责重叠时模型会选错。宁可合并也不留重叠。

## 与 pi 的三处差异及理由

| 差异 | 理由 |
|---|---|
| search 合并 grep + find | 约束 B：落盘逻辑只写一处 |
| bash 只接受数组参数 | 字符串必过 shell 解析，是注入面 |
| 新增 task 工具 | 后台任务是真实需求；pi 没有，DSH 用三个工具覆盖，这里用一个工具的 4 个 action |

## 代价

- bash 不接受字符串，管道与重定向要拆成多次调用；
- search 多一个 mode 参数；
- task 的 4 个 action 让 schema 略复杂。
