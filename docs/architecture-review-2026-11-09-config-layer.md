## 1. L-1：新增默认层依赖的准入四问（P1）

### 1.1 现象

默认层新增 `noyalib`（YAML 1.2 解析）用于读取 `~/.toolgate/config.yaml`。
§1.5 规定「新依赖逐条回答，答不上就不引入」，§19.6 规定「新增项走 §1.5 的
准入四问，并同时更新本表与附件 E.8」。若台账只加一行、不写准入论证，
「最少依赖」这条设计原则就没有留下可复核的记录——后来人无法判断这是权衡后的
结论还是随手加的。

### 1.2 选型证据

三个候选的 crates.io 元数据（2026-11-09 查 crates.io API 与 `cargo info`，
详见附件 E.8）：

| 候选 | crates.io 最新版 | updated_at | 维护状态 |
|---|---|---|---|
| `serde_yaml` | 0.9.34+deprecated | 2024-03-25 | 官方仓库已归档停更；版本号本身带 `+deprecated` 后缀 |
| `serde_yml` | 0.0.13 | 2026-05-27 | crates.io 描述首行即「DEPRECATED — `serde_yml` is unmaintained」，并说明它是转发到 `noyalib` 的兼容壳 |
| `noyalib` | 0.0.58 | 2026-10-15 | 活跃维护；YAML 1.2；纯 Rust、`#![forbid(unsafe_code)]`、serde 集成完整 |

结论：默认层用 `noyalib`。用 `serde_yml` 的路径最终也落到 `noyalib`
（它自己就这么写），用 `serde_yaml` 则等于绑定一个已停更的仓库。

### 1.3 准入四问逐条回答

| 问 | 答 | 依据 |
|---|---|---|
| 1. 标准库能否完成？ | **不能** | 标准库无 YAML 解析。手写 YAML 1.2 解析器要处理标量类型推断、缩进与块结构、锚点 / 别名、多风格引号与转义——边界条件多且易错，且 §18.9 要求报「文件:行:列」，自写还要额外做位置跟踪 |
| 2. 现有依赖能否完成？ | **不能** | `serde` 只做数据结构映射不解析格式；`serde_json` 只解 JSON，解不了 YAML 的块语法与锚点；默认层无其他格式解析器 |
| 3. 会进默认层吗？ | **会**，且不能做成可选层 | 配置读取是默认构建的必备路径：连「文件不存在 → 用内置默认」这条都要能读文件才能判定（§18.9、附录 D）。做成 feature 会让默认构建与开启 feature 出现两套配置语义。传递依赖规模实测 19 个（附件 E.8） |
| 4. 会破坏纯 L0 版的单二进制吗？ | **不会** | 纯 Rust、`#![forbid(unsafe_code)]`、无 C/C++ 绑定、无动态库、无平台框架；不引入 native 依赖；`cargo build --release` 仍产出单个可执行文件（§19.3） |

### 1.4 落点

- §19.6 默认层表格新增 `noyalib` 一行（用途、理由含「纯 Rust 零 unsafe，不破坏
  纯 L0 版单二进制」），并在依赖方向约束补一条：**配置解析与协议编解码同类，
  归默认层**；
- 附件 E.8 新增「YAML 解析库的选型证据」小节（三条证据 + 子树构成 + 版本口径）。

## 2. L-2：`adapter: auto` 规则的空白（P1）

### 2.1 现象

§3.10 原文写「`source: local` 且模型在参考实现清单 → `native`」。「在参考实现
清单」是**不可由配置判定**的条件：配置里只有模型 id、`path` / `base_url`、
`serves`，解析器无法知道 `path` 指向的权重是不是 jev（附件 E.2 的清单是文档
里的模型族名单，不是配置可读的事实）。规则不可判定，实现者只能二选一：维护一份
模型名单去猜，或忽略这半句。

两种猜法都会出错。按名单猜：用户填了非清单里的本地模型时，猜不中就走 `json`，
而它本可能原生输出概率（丢掉校准能力）；猜中但用户换了个同族权重时，走
`native` 却拿不到原生输出——**非原生模型被按 `native` 调用时，既拿不到校准
概率，又丢掉了 §4.4b 的 `UNCALIBRATED` 告知**，这是最坏组合。

### 2.2 精确化

规则只依据**配置里能判定的事实**（`source` 与目标槽位）：

| 条件 | adapter |
|---|---|
| `source: local` | `native` |
| 外部协议 → 槽位 `classify` / `decide` | `json` |
| 外部协议 → 槽位 `summarize` / `vision` | `text` |
| 外部协议 → 槽位 `rerank` | `ordered` |
| 无法判断 | `json` |

并写明 `native` 是**初值不是保证**：模型是否真的按槽位契约输出由首次使用的
形状校验确定，不符按 §3.11 降级或禁用并告警（§18.9 的「能力不符」层）。

### 2.3 落点

03-slots.md §3.10「形状适配：能力与形状分开」小节：替换原句为上表 + 两段说明
（为什么不再写「在参考实现清单」、`native` 只是初值）。

## 3. L-3：`config check` 的行为约定（P2）

### 3.1 现象

§18.9 写了 `toolgate config check`「只做语法 / 结构 / 语义三层校验」「输出与
启动时一致的可行动错误」，但**没定义「配置文件不存在」算什么**。这直接决定实现
分叉：

- 若一律判错 → 第一次跑 `config check` 的人看到红色报错，但「无配置文件也能
  启动」才是默认形态（附录 D），报错会让人以为装坏了；
- 若一律放过 → 用户 `--config /path/typo.yaml` 检查通过，以为检查的是那份配置，
  其实检查的是内置默认。**静默通过比报错更糟**（§1.4.4）。

### 3.2 约定

| 情形 | 判定 | 理由 |
|---|---|---|
| 默认路径（`~/.toolgate/config.yaml`）不存在 | **不是错误**：用内置默认，退出码 0 | 「无配置文件也能启动」是默认形态 |
| 显式 `--config <path>` 指定但文件不存在 | **是错误**：报可行动错误，退出码非 0 | 用户点名了这个路径，路径写错最可能；静默通过等于让用户以为检查过的是那份配置 |

配套：**错误聚合**（多错误一次列全，与 §18.9「错误格式：可行动」同口径）、
**退出码**（有错误时非 0，与 `serve` 一致）。

### 3.3 落点

18-deployment.md §18.9「启动前自检：`toolgate config check`」小节：补上述两行
判定表与聚合 / 退出码说明。

## 4. L-4：未实现配置段的处理策略（P2）

### 4.1 现象

附录 D 的默认值表覆盖 `intent` / `isolation` / `paths` / `limits` / `spill`
/ `snapshot` / `cache` / `logging` / `fetch` / `govern` 十段，但本轮只实现
并消费 `models` / `slots` / `slm` 三段。这十段在配置里出现时该发生什么，
架构正文原本没写。

风险在 §18.9 的「未知字段一律拒绝」策略上：如果这十段按未知字段处理，用户看到的
错误是「你拼错了字段名」，而他没拼错——字段在架构里存在，只是还没接线。这个误
导会让用户反复检查拼写，而不是去查「这功能到底有没有实现」。

### 4.2 策略

按 §18.9 的**结构层**失败处理：报出该段名并说明「当前版本未实现该配置段」的可
行动错误，**不静默忽略**。理由与未知字段拒绝同源——静默忽略会制造配置幻觉，
用户以为配了会生效（附录 D 的默认值表是完整配置面，不是已实现清单）。

### 4.3 落点

90-appendices.md 附录 D：在「默认值」表之后新增「本版本已实现的配置段」小节，
用表格标出三段已实现（`models` / `slots` / `slm`）与其余十段「配置参考、
尚未接线」，并写明未接线段配了会被明确拒绝及其理由。

## 6. L-6：三层校验的层间关系与枚举值拼写（P3）

### 6.1 现象

两处口径在实现落地时暴露出来，原文没写：

1. **层间关系**：§18.9 说「一次报全部错误」，但没说层与层之间是并行收集还是短路。
   实现按短路做：语法错只报一条（带文件路径与行列位置）→ 结构层错误一次列全
   后**立即返回，不跑语义层** → 语义层一次列全。短路的理由是结构不完整时
   语义校验只会产生连锁噪音（`models` 没定义时，`slots` 的引用会报一堆无意义的
   「模型不存在」）。
2. **枚举值拼写**：附录 D 写 `slm.probe` 默认值 `first-use`、取值
   `first-use / startup / off`，实现按 serde 的 snake_case 取 `first_use`。
   连字符与下划线混用会让用户写出 `first-use` 后被结构层拒掉。

### 6.2 补齐

- §18.9「四层校验」节补一段**层间短路关系**表（语法 → 结构 → 语义），并写明
  「短路不是少报错误：每层内部仍一次列全，只是下游层不基于不完整结构继续推断」；
  同时写明语法层错误码 `CONFIG_SYNTAX`（`field` 是文件路径，行列位置放在 `fix` 里）；
- 附录 D 的 `slm.probe` 默认值与取值改为 `first_use / startup / off`。

### 6.3 落点

18-deployment.md §18.9「四层校验」节；90-appendices.md 附录 D「默认值」表。

## 7. L-7：§19.6 曾清退 CLI 的 `tracing`，配置层落地后重新需要它（P3）

### 7.1 现象

§19.6 的「不用就不声明」记录着：v1 骨架遗留的未使用声明（core 的 `anyhow` /
`tracing`、mcp / cli 的 `tracing`）已于 2026-11-08 清退。CLI 接入配置层后要写
启动日志（§18.9「降级必须写进启动日志」），用 `tracing::warn!` 实现。

**`tracing` 只是 `tracing-subscriber` 的传递依赖，CLI 不直接声明就编译不过**
（`error[E0433]: failed to resolve: use of undeclared crate or module `tracing``）——
宏调用必须显式声明依赖。所以这不是「又引入一个用不上的依赖」，而是这条原则的
正常应用：用了才声明。

### 7.2 补齐

- §19.6 默认层表格新增 `tracing` 行（用途「CLI 侧日志调用门面（宏）」），并写明
  理由：日志实现是 `tracing-subscriber`，`tracing` 只是门面；core 库不依赖它，
  日志仍只进 CLI；
- §19.6 依赖方向约束补明：**CLI 可直接依赖 `tracing`**（与日志实现同在边界层），
  但 **core 库不得依赖 `tracing` 或 `tracing-subscriber`**，原边界不变；
- §19.6「不用就不声明」那条的清退记录修正为：清退的是 core 的 `anyhow` /
  `tracing` 与 mcp 的 `tracing`（CLI 的 `tracing` 现已重新声明），并写明重新声明
  的理由；
- 附件 E.8 同步：直接依赖 16 → 17、默认构建规模 106 → 109 行、`Cargo.lock`
  96 → 98 个包、新增 `tracing` 子树（11）、`--duplicates` 新增一组 `syn`
  2.0.119 / 3.0.9（`tracing-attributes` 与既有宏链的 proc-macro 依赖不兼容）。

### 7.3 落点

18-deployment.md §19.6（默认层表格 + 依赖方向约束 + 「不用就不声明」条）；
95-references.md E.8（基线数字、子树表、同名多版本现状、结论段）。

## 9. 遗留

1. **实现与正文的偏差需在实现侧收口**：本报告定下的 `config check` 判定（默认
   路径不存在不算错、显式指定不存在算错、多错误聚合、退出码非 0）与「未接线段
   明确拒绝」，需与 CLI 的实际实现逐条对齐；若实现选了另一条口径，改的是实现，
   不是正文。core 层的 `load_config` 对「默认路径」与「显式 `--config`」一律返回
   `Ok(None)`，两种情形的区分在 CLI 层做。
2. **未接线段的用户可见文案未逐段定制**：架构只规定「报出段名 + 说明未实现 +
   可行动」，每段的具体建议文案由实现决定，不在架构层规定。
3. **`noyalib` 版本受 MSRV 约束**：`Cargo.lock` 锁 0.0.15（`rust-version` 1.85.0），
   crates.io 最新 0.0.58 要求 `rust-version` 1.89.0，仓库 `rust-version = "1.85"`
   故由 cargo 的 MSRV 感知解析选到 0.0.15。抬 `rust-version` 后可升版，但按 §19.6
   的「`cargo update` 单独提交」纪律走，不与功能改动混在一起。
4. **`slots` 显式覆盖与 `serves` 自动推导的边界**：本轮实现固定按 `SlotKind::ALL`
   顺序产出 5 条绑定（空槽位也在其中，标记为不可用）。若后续要让绑定顺序随配置
   变化，属实现细节，不动架构。
5. **`syn` 的同名多版本**：CLI 重新声明 `tracing` 后，锁文件里同时存在 `syn`
   2.0.119（`tracing-attributes` 链）与 3.0.9（serde / thiserror / tokio 宏链）。
   两条链的 proc-macro 不兼容，`cargo` 不做版本合并。若要消除，需等上游宏生态
   收敛到同一 `syn` 主版本；本轮不为此做版本覆盖（§19.6 的「禁止版本通配」）。
