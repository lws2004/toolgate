## 3. 本地模型层：能力槽位

### 3.0 架构定义槽位，不定义模型

本架构**不绑定任何具体模型**。它定义的是六个**能力槽位**，每个槽位有
确定的输入输出契约与延迟预算；具体模型是可替换的实现。

**决策：架构只定义槽位契约，不写死具体模型。** 写「判定槽位需要一个能在
30ms 内输出带概率答案的模型」，换谁都能跑；写死模型名会让模型停更、改许可证
或出现更强替代品时，架构跟着改。

**本文档 §3.1-3.3 讲槽位契约；参考实现见附件 E.2。**

### 3.1 六个槽位

| 槽位 | 输入 | 输出 | 延迟预算 | 必需特性 |
|---|---|---|---|---|
| classify | 文本 + 候选标签集 | 每个标签的分数 | < 20ms | 输出受限、带分数 |
| rerank | query + N 个候选 | N 个相关度分数（保序） | < 100ms / 批（block_size=125）；N=300 总 < 300ms | 批处理、可排序 |
| decide | state（文本/JSON/图）+ 命名问题 | 每个问题的概率（+ 可选 span） | < 30ms | 输出受限、带概率 |
| summarize | 有界文本（≤ prefill 预算，见 §6.4） | 文本或 JSON | < 1s | 生成、结构化输出 |
| vision | 图片 + 问题 | 文本 / 坐标 / OCR 文本 | < 2s | 多模态、grounding |
| embedding | 文本 / 文本批 | 定长向量（维度由模型定，同一批内一致） | < 100ms / 批（N≤32；本机实测 71ms，E.3.2） | 向量化、维度一致 |

**六个槽位不是按模型分的，是按「答案形状」分的**：

- classify 的答案形状是「标签 → 分数」，候选集固定、数量少；
- rerank 的答案形状是「候选 → 分数」，候选集可变、数量多；
- decide 的答案形状是「问题 → 概率」，问题集固定、可能带多模态输入；
- summarize 的答案形状是「一段文本」，长度不定；
- vision 的答案形状是「对图的描述或坐标」，需要视觉编码；
- embedding 的答案形状是「文本 → 定长向量」，用于语义相似度与重排，无天然分数，由下游计算余弦。

**延迟预算必须绑硬件档位。** 上表的数字是 **H100 口径**；同一批模型在 Apple
Silicon 上的实测延迟高出一个档（§6.3：d1 从 5.7ms 变成数十 ms，LFM3 从数百 ms
变成约 1s）。按统一预算去筛实现，在 Apple Silicon 上会把所有候选都判为不合格
——那预算就失去了筛选作用。

**这些预算都不含 prefill 与固定开销。** 本机实测（§6.4）的固定开销已超过 decide
槽位的 30 ms 预算。所以本表是 H100 短输入口径的**推理延迟**，不能直接当
端到端筛选尺子。六个槽位中五个在 2026-11-07 有本机实测值；embedding 于 2026-11-13 实测了输出正确性
（bge-m3，见附件 E.3.2），其延迟预算仍属估算；H100 口径的数字在本机无一成立。

| 槽位 | H100 档（短输入推理口径） | Apple Silicon 档（本机实测，2026-11-07） | CPU 档 |
|---|---|---|---|
| classify / decide | <20 / <30 ms | 按 prompt token 分档：d3-nano 137 / 231 / 644 ms，StartLux 350 / 708 / 2745 ms（50 / 200 / 800 词 state） | 不建议 |
| rerank | <300 ms（N=300） | 按候选数：94 ms（N=10）/ 1.8 s（N=125）/ 5.2 s（N=300） | 不建议 |
| summarize | <1 s | 36.4 ms 固定开销 + 1703 tok/s prefill；50KB 约 7.6 s | 不建议 |
| vision | <2 s | 按图像 token：264 ms（191 token）/ 5.2 s（2831 token） | 不建议 |

Apple Silicon 列来自 2026-11-07 本机实测（Apple M2 Max / 96 GiB，附件 E.3.2），按输入规模分档，不再是单一阈值；它只作观测与选型基线，不作运行时门控（§7.3）。H100 列仍是短输入推理口径，不含 prefill 与固定开销。

**延迟预算是观测与选型基线，不是运行时门控，也不是模型的能力上限。** 用 30B 模型跑 decide 会得到
更好的判断，但延迟从 30ms 变成数百 ms——那是错配，不是升级。槽位要的是
「低延迟专用件」，agent 要的是「高延迟通用件」，两者不互相替代（§6.3）。

### 3.2 槽位契约

每个槽位的契约用「输入 → 输出」的确定性描述，实现必须遵守。**槽位只提供单步契约**；多步理解由工具层的理解链编排（§4.8），槽位不感知链。

**classify**

```text
输入: { text: string, labels: string[] }        labels 长度 2-50
输出: { scores: { [label]: number } }           每个分数在 [0,1]
约束: scores 的 key 集合必须等于 labels；不生成任何额外文本
```

**rerank**

```text
输入: { query: string, documents: string[], top_n?: number }
输出: { results: [{ index: number, score: number }] }  按 score 降序
约束: results 覆盖全部输入文档；index 指向原始位置；不改变文档内容
```

**decide**

```text
输入: { state: string | object, images?: Image[], questions: string[] }
输出: { answers: { [question]: { probability: number, span?: [number, number] } } }
约束: 每个问题一个概率；span 仅在要求定位时返回；不生成自由文本
```

**summarize**

```text
输入: { text: string, schema?: object, max_tokens?: number }
输出: { text: string } 或 { data: object }（有 schema 时）
约束: temperature = 0（保证同输入同输出，见 §16.3）；输出按 schema 校验
```

**vision**

```text
输入: { image: Image, task: "describe" | "ocr" | "ground" | "classify", query?: string }
输出: { text?: string, boxes?: [{ label, bbox: [x,y,w,h] }] }
约束: task=ground 时 boxes 必填；bbox 用原图像素坐标
```

**embedding**

```text
输入: { texts: string[] }              texts 长度 1-32
输出: { vectors: number[][] }          与 texts 等长、同序；每条等维（维度一致）
约束: vectors 数量等于 texts 数量；同一批内维度一致；不改变原文本
```

### 3.3 替换实现的判据

换一个模型进来，必须**同时**满足四条：

| 判据 | 怎么验 |
|---|---|
| 可适配性 | 模型原生输出契约形状（`native`），或能通过适配器稳定转成该形状（`json` / `text` / `ordered`）；转形状后的概率不是校准概率，必须标注（§3.10） |
| 延迟在预算内 | **在本机所在档位上实测**，不是官方标称（官方数字通常是 H100 口径）。实测值只用于校准档位表与选型参考；达不到不触发降级（§7.3），也不据此关闭槽位 |
| 许可证允许用途 | 商用场景排除 cc-by-nc 类许可 |
| 中文能力达标 | 用本项目的中文样本实测，不看官方声称支持多少语言 |

**「输出形态匹配」不再是「模型必须原生输出概率」**：通用 LLM 也能做判定，只是
需要适配器把它输出的 JSON 转成槽位形状（§3.10）。但适配后的概率是模型自报值，
不是校准概率——高风险判定只能用原生实现，或由云端复核（§7.2）。

第三条容易被忽略。当前参考实现里就有一个 cc-by-nc-4.0 的模型（§3.4），
它只能用于非商用场景。

### 3.4 参考实现的选型原则

参考实现（StartLux / d3-nano / jina-reranker / LFM3 / LFM3-VL）属于选型记录，
不是架构的一部分，完整清单与口径见附件 E.2。架构只约束：每个槽位按 §3.3 的
四条判据选实现，参考实现可替换。

**参考判定模型属 systemone 协议族，不按 chat 协议工作**（2026-11-09 本机实测）：
StartLux / d3-nano 是 jev 类判定模型，走 `/v1/systemone`（命名问题 → 校准概率，
§18.1）才是正确形态。**用通用 chat 协议调用它们会得到退化输出**——实测 d3-nano
经 llama-server 的 `/v1/chat/completions` 返回 `finish_reason=length` 且内容是重复
token 序列（形如 `IAHO-YA-IH` 循环，无语义）。

**遇到这种输出不要误判成「模型坏了」**：判据是 `finish_reason=length` + 重复
token 序列——这是「用错协议」的特征，不是「模型加载失败」或「权重损坏」。
正确处理是改用 systemone 协议（§18.1 的 `source: systemone`），不是去换模型。

### 3.5 为什么 rerank 必须独立成槽位

用 classify/decide 类模型做 rerank 在原理上可行，但成本结构不对：

- decide 槽位：一个 state + 一组由调用方一次给定的问题，输出每个问题的概率。
  **输出条目数等于问题数，与 state 长度无关**；问题集在调用内固定，一次前向搞定。
- rerank 槽位：一个 query + N 个候选，输出 N 个分数。**N 随命中数变化**。

用 decide 做 rerank，等于对每个候选问一次「这条相关吗」——N 次前向。
而 listwise reranker 一次前向处理一整块候选（参考实现是 125 个），
300 条命中只需要 3 次前向。

这就是为什么 rerank 必须是独立槽位：**它的输出规模随候选数变化，且输出必须保序、覆盖全部输入**；
而 decide 的输出规模由调用方给定的问题集决定，与 state 长度无关。这个差别决定了两者不能共用一个实现。

### 3.6 为什么 vision 与 decide 都保留

视觉槽位和判定槽位可能由同一个基座模型提供（参考实现里 d1 的基座
就是 LFM3-VL-2B），但**输出形态不同**：

- vision 做**生成**：描述图里有什么、OCR 出文字、给出坐标。输出是自由文本。
- decide 做**判定**：在给定问题集上给概率答案。输出受限。

一个具体例子，给一张报错截图：

- 用 vision：「图里有一段红色报错文字，内容是 TypeError: undefined is
  not a function」—— 可能漏细节、可能编。
- 用 decide 问「图里有报错吗？报错类型是什么？严重吗？」—— 判定，
  输出受限、带概率、可以门控。

**要生成内容用 vision，要判定用 decide。** 同一个基座，两种用法。

### 3.7 选型判据树

```text
要一个「几选一的答案」？
  ├─ 纯文本、候选集小 → classify 槽位
  ├─ 需要看图 → decide 槽位（需多模态实现）
  └─ 问题集固定、要 span → decide 槽位
要「给一批候选排序」？
  └─ rerank 槽位
要「一段生成的文字 / JSON」？
  └─ summarize 槽位
要「图里有什么 / 在哪 / 什么字」？
  └─ vision 槽位
要「规划、写代码、多步推理」？
  └─ 云端
```

这张判据树的每一步都是「答案形状」问题，不是「模型大小」问题，
也不是「用哪个厂商的模型」问题。

### 3.8 槽位可空：一个都不配也能跑

**核心保证：槽位是增强，不是依赖。**

六个槽位全部为空时，toolgate 退化成一个「治理良好的工具层」——仍然比裸工具强，
因为治理规则全是纯机械的，不依赖任何模型：

| 治理能力 | 是否依赖模型 |
|---|---|
| 双阈值截断 | 否 |
| 落盘 + 指针 | 否 |
| 类型嗅探（魔数） | 否 |
| 图片压缩流水线 | 否（image crate） |
| 编码与行尾保真 | 否 |
| 写前快照 | 否 |
| 编辑三模式 | 否 |
| 脱敏（正则） | 否 |
| 缓存保护（确定性输出） | 否 |

**消费点（2026-11-13）**：classify 用于 bash / search / task 的输出敏感度标注
（§5.1 / §5.2 / §5.5），与机械正则取更高等级；read 的类型与敏感度仍由 decide
十问归并（§5.3）；
embedding 用于 search 的重排退路（§5.2）与 decide / summarize 输入的近重复合并
（§5.1 / §5.3 / §5.5），都是单次调用内、无索引、无持久状态。

#### 逐个槽位缺失的影响

| 缺失 | 失去什么 | 降级行为 | 还能用吗 |
|---|---|---|---|
| classify | 类型与敏感度判定、输出敏感度标注 | 类型/敏感度按扩展名与魔数机械判定；输出标注由正则与 classify 取高（正则保底）；脱敏仍走正则 | 是 |
| rerank | 候选重排 | embedding 可用则按余弦重排；否则按命中顺序返回（遍历顺序稳定） | 是 |
| decide | 所有判定 | 全部走原始路径：不判错、不判类型、不判 need_pixels | 是 |
| summarize | 摘要与结构化 | 给截断后的原文 + 落盘指针 | 是 |
| vision | 图片理解 | 压缩后返回原图（上游支持视觉时）；否则返回文件元信息 + 路径，让模型自己决定 | 是 |
| embedding | 语义重排、模型输入语义去重（单次调用内） | 重排：rerank 可用时无影响，rerank 不可用且命中 > 20 时按余弦重排；去重不可用时用原窗口；两者都不可用按命中顺序返回 | 是 |

#### 全部缺失时的形态

- read：读文件、编码保真、截断、图片压缩后返回原图
- bash：执行、截断、落盘
- search：检索、截断、落盘
- edit：三种模式、行尾保真、写前快照
- task：进程管理、增量读取
- write：写入、快照

**这就是 v1 的形态**。它已经解决了「上下文爆炸」与「文件被破坏」两个问题，
只是没有解决「哪些东西不该上传」。

所以价值排序是：

```text
1. 机械治理（必须）—— 解决正确性问题：不丢信息、不破坏文件
2. 本地模型（增强）—— 解决效率与隔离问题：少传、少花
```

**先保证不坏，再优化。** 这个排序决定了：没有本地模型的部署仍然是
可用的产品，而不是「功能不全的演示版」。

#### 槽位之间的解耦

部分配置时各槽位独立生效：

| 配置 | 能做什么 | 不能做什么 |
|---|---|---|
| 只有 summarize | bash 输出可摘要 | read 不判 need_pixels，默认给原图 |
| 只有 decide | 判错、判类型 | 不能摘要，给截断输出 |
| 只有 vision | 图片可理解 | 文本输出不摘要 |
| decide + summarize | 判错后摘要（完整链路） | —— |

解耦的代价：有些优化需要多个槽位配合，缺一个就只生效一半。但不会报错。

#### 配置形态

**配置只写模型清单，不写槽位清单**：

```yaml
models:
  jev:     { path: ~/.toolgate/models/jev, serves: [classify, decide] }
  lfm3-vl: { path: ~/.toolgate/models/lfm3-vl, serves: [summarize, vision] }
```

- `models`：有哪些模型；每个模型用 `serves` 声明「它能服务哪些槽位」；
- `slots`：**可省略**。只在要显式覆盖某个槽位的绑定时才写（§3.10）。

六个槽位不需要逐个配置：上面两行覆盖四个槽位（rerank 与 embedding 未配 → 空，§3.8）。
模型还可带 `mode` / `backend` 两个部署字段（embedded | http），不写时继承 §18.1 的
分档表；它们只影响模型怎么跑，不改变槽位契约。**同一模型服务多个槽位时只有一个
部署模式**，模型级设置优先于槽位默认。

**没有 enabled: false 这种开关**：不写就是没有。少一个开关，少一处状态不一致。

### 3.9 能力可扩展：模型升级后承担更多

槽位契约定义的是**最低要求**，模型可以超出。三种扩展方式：

| 扩展方式 | 例子 | 架构要不要改 |
|---|---|---|
| 一个模型填多个槽位 | MiniCPM5 同时擅长判定与摘要 | 不改，models 的 `serves` 声明（§3.10） |
| 槽位内能力增强 | summarize 从「只出文本」升级到「能出结构化 JSON」 | 不改，槽位契约已覆盖；首次调用校验（见下） |
| 新增槽位 | 出现专门做「代码理解」的模型 | 加一个槽位定义，其余不动 |

#### 槽位内能力：契约定义，首次校验

槽位契约（§3.2）已写明每个槽位的最低输出要求。模型支持超出最低要求的能力
（结构化输出、更长上下文）时**不单独配置**：

- 支持 → 调用成功，自动可用；
- 不支持 → 按 §7.3 降级（如 intent=structured 退回 text），并按 §4.4b 的 `DEGRADED` 告知。

这样模型升级只换 `models.<id>.path`，配置不增加字段。

#### 为什么是 serves 声明 + 首次校验

`serves` 声明的是「这个模型能接哪些槽位」——槽位是固定词汇（§3.1），声明可审计、
可回滚。槽位内的具体能力不做配置声明，用首次调用校验：模型实际不支持时调用失败，
记录并把该能力标记为不可用，避免反复失败。

运行时探测更准确，但要求模型能自描述能力——目前没有标准格式，所以配置声明
（serves）为主、首次校验兜底。

#### 一个具体的升级路径

从 LFM3-1.7B 换到更强的模型：

```text
1. 改 models.lfm3-1.7b.path（换权重）
2. 如果新模型能服务更多槽位，改它的 serves
3. 工具自动用上新能力，架构文档一行不改
```

这就是 §3.0 说的「换模型不动架构」的具体操作。

### 3.10 配置简化：槽位、模型与绑定

**先把三个概念分开**——混在一起才难理解：

| 概念 | 是什么 | 谁定义 | 配置里怎么写 |
|---|---|---|---|
| 槽位 | 能力契约的固定词汇表：classify / rerank / decide / summarize / vision / embedding | 架构（§3.1） | **不出现在配置里**（除显式覆盖） |
| 模型 | 一个可加载的推理实例（权重 + 后端） | 用户 | `models`：id、path、`serves`（能服务哪些槽位） |
| 绑定 | 某个槽位由哪个模型承担 | 解析结果 | `slots`：可选的显式覆盖；不写就自动推导 |

**配置只需要写模型清单**：

```yaml
models:
  jev:
    path: ~/.toolgate/models/jev
    serves: [classify, decide]      # 能服务两个槽位
  lfm3-vl:
    path: ~/.toolgate/models/lfm3-vl
    serves: [summarize, vision]     # 只配这一个模型：summarize 与 vision 都可用
```

- 六个槽位不写全：上面 2 个模型覆盖 4 个槽位，rerank 与 embedding 为空（§3.8 降级）；
- 同一个模型服务多个槽位只声明一次（在 `models` 里），**不在槽位下重复写槽位名**；
- `source` 默认 `auto`（有 `path` 用本地权重，有 `base_url` 按 URL 推断协议）；显式取值以 §18.1 的 source 表为准（唯一事实源，不在此重复维护），其中 `systemone` / `rerank` / `embedding` 不参与 auto 推断；
- `adapter` 默认 `auto`（按来源与槽位推断），可显式 `native` / `json` / `text` / `ordered`（见下）。

**解析规则**：

1. `slots.<name>: <model-id>` 写了 → 显式覆盖；
2. 否则：`serves` 含该槽位的模型里，显式写了 `source: systemone` 的优先（§18.1
   「能用 systemone 的模型就用它」）；没有再按 `models` 声明顺序取第一个；
3. 都没有 → 该槽位为空（§3.8）。

**不做同一次调用的跨协议重试**：协议在配置期选定，运行时源不可用按 §3.8 降级到
L0、形状不符按 §3.11 降级并告警，不临时换另一个协议重发——两条路径的概率性质
不同（校准 vs 自报），换协议会让同一次返回的语义漂移。

**显式覆盖示例**（可选，不写也行）：

```yaml
slots:
  summarize: lfm3-vl    # 强制指定；其余槽位仍自动解析
```

**为什么这样更清楚**：

- 槽位是固定词汇，不是配置项——配置里不再出现「classify: {model: ...}」这类逐项清单；
- 「能服务什么」是模型自己的属性，写在模型下（`serves`），不写在槽位下；
- 绑定是推导结果，不是配置主体；
- 只有一个能力声明字段（`serves`），没有 provides / features 两个近义概念。

**复用前提（不因简化而放松）**：`serves` 只是「可服务」的声明，不是能力保证。
实际使用要过 §3.3 的四条判据（输出形态、延迟预算、许可证、中文能力）与输出契约
（§3.2）；首次调用校验失败时标记该槽位不可用（§3.9）。

**歧义**：多个模型都 serves 同一槽位时，按 models 顺序取第一个；要指定用哪个，
写显式 `slots.<name>`。

**不改变的东西**：

- 槽位契约不变：同一模型服务多个槽位时，仍按目标槽位的输入输出契约调用（§3.2）；
- 空槽位语义不变：没有模型服务 → 该槽位为空（§3.8）；
- 可审计：启动日志与 `toolgate list` 打印每个槽位最终绑定的模型与来源（显式 / 自动）。

#### 形状适配：能力与形状分开

`serves` 声明的是**语义能力**（能不能做这类理解），不是**输出形状**。同一个模型
可以做决定，但输出可能是自然语言、JSON 或原生概率。适配器负责把槽位请求转成
模型输入、再把模型输出转回槽位契约（§3.2）的形状：

| `adapter` | 做法 | 质量 | 适用 |
|---|---|---|---|
| `native` | 模型原生按槽位契约输出 | 校准概率 / 受限输出 | jev 类、专用 reranker |
| `json` | 要求模型输出 JSON schema，解析成槽位形状 | 自报概率，非校准，必须标注 | 通用 LLM 做 classify / decide |
| `text` | 纯文本或 JSON 直接映射 | 无概率 | summarize / vision |
| `ordered` | 输出排序列表或分数 | 排序可用、分数非校准 | rerank |

默认 `adapter: auto`，规则只依据**配置里能判定的事实**（`source` 与目标槽位）：

| 条件 | adapter |
|---|---|
| `source: local` | `native` |
| `source: systemone` → 槽位 `classify` / `decide` | `native` |
| `source: rerank` → 槽位 `rerank` | `native` |
| `source: embedding` → 槽位 `embedding` | `native` |
| 外部协议（`openai` / `anthropic` / `responses`）→ 槽位 `classify` / `decide` | `json` |
| 外部协议 → 槽位 `summarize` / `vision` | `text` |
| 外部协议 → 槽位 `rerank` | `ordered` |
| 无法判断 | `json` |

`source: auto` 先按 §18.1 的判定顺序推断成具体来源，再套用本表（推断出 `local`
走 `native`）；推断不出来按最后一行处理。

**术语**：本表的「外部协议」特指通用 LLM 三协议（`openai` / `anthropic` / `responses`）；§18.1 的「外部来源」是更大的集合，另含 `systemone` / `rerank` / `embedding` 三个独立协议族，三者不互换。

#### 跨槽位服务的准入：信息充分 ∧ 形状可转换

**槽位形状固定**（§3.2）：六个槽位的输入输出契约不随模型变；`serves` 只声明
「能服务哪类语义理解」，不声明输出形状（本节的「形状适配」）。

**一个模型要服务非原生槽位，两条必须同时成立**：

| 判据 | 内容 | 反例（为什么不成立） |
|---|---|---|
| 输入信息充分 | 目标槽位契约要求的输入信息，都在该模型能拿到的输入里 | 判定模型只给概率、不生成 token，也没有候选集排序接口，拿不到 `summarize` 的文本输出通道与 `rerank` 的候选打分 |
| 输出形状可转换 | 模型输出能稳定转成目标槽位的契约形状（本节适配器表） | 把 `choice` 的 `confidence` 当 `probability`，是把「选项间相对置信」与「二元肯定概率」混成一个量，属静默转换，禁止（见下） |

**判据的落点是 §18.1 的协议能力表**：表里每个「不可用 / 受限」都必须能归到
这两条之一；`classify` 对 systemone 判「可用」是形状可转换且映射已落（见下），不是信息不足；
`rerank` 协议对其余五个槽位标「不可用」是只返回排序结果、缺文本 / 概率 / 图像输出
通道（输入信息不足），而 `rerank × rerank` 的「可用」是信息充分且形状可转。
**这张表在代码里由 `capability` 模块固化为唯一可执行落点**（`source × slot` 判定）：
§18.1 的文档表是权威描述，代码判定与它逐格一致，不得各自演化出不同结论。

**与 §3.11 的分工**：`serves` 是声明不是承诺，声明阶段不因这条判据拒绝配置
（前三层的 fail loud 仍按 §18.9）；能力判定是**运行时的前置准入**，最终以首次
使用的形状校验为准，判定为不可用 / 受限时按 §7.3 给可行动理由并降级。

#### systemone 适配器：槽位形状 ↔ 命名问题

systemone 的原生形状最接近 §3.2 的 decide 契约，因此走 `native`（不是 `json`）——
它直接给校准概率，不需要「要求模型输出 JSON schema 再解析」这一层转换。映射规则：

| 方向 | 映射 |
|---|---|
| 槽位 decide → 协议 | 槽位的 `questions`（字符串数组）按序编号成命名问题 `q0` / `q1` / …；每个问题的 `type` 固定 `noul`，`instructions` 写问题原文；`state` 写槽位输入的文本 / 对象 |
| 协议 → 槽位 | 每个 `noul` 答案的数值 → 对应问题的 `probability`；问题名 `q0` / `q1` 按序还原回槽位问题的顺序 |
| 概率语义 | `noul` 是「该问题的肯定回答为真的概率」，与 §7.2 门控同向：`p ≥ 0.85` 采用、`0.60 ≤ p < 0.85` 标 LOW_CONFIDENCE、`p < 0.60` 两视图都给 |

**classify 走 `choice`**（§18.1 能力表「可用」）：

| 方向 | 映射 |
|---|---|
| 槽位 classify → 协议 | 单个命名问题 `q0`：`type: "choice"`，`instructions` 固定措辞，`criteria` 为 `{<标签>: <标签>}` 的 map（官方 `criteria` 的键是选项名、值是描述；槽位只有标签名，用标签名本身，不注入额外语义）；`state` 写 `input.text` |
| 协议 → 槽位 | `probabilities` 按标签名一一映射成 `scores`；`choice` / `confidence` 不参与映射 |
| 概率语义 | `probabilities` 是校准的逐选项概率（和为 1），产出 `calibrated: true`；`none_probability ≥ 0.2`（官方建议阈值，附件 E.10）表示「无合适选项」，本次按 §3.11 形状不符降级，不返回分数 |

缺标签、类型不符、概率越界、`none_probability` 越阈值都按 §3.11 降级并给可行动理由。

**decide 只接受 `noul` 类型，classify 只接受 `choice` 类型**。§3.2 的槽位契约
**没有类型维度**——decide 只问「这个问题的概率是多少」，classify 只问「每个标签的分数」。
协议另有 `score` 类型，两个槽位都不用它；类型不符按 §3.11 的「形状不符」处理
（该次降级、连续失败后禁用该槽位并告警），**不做静默转换**——把 `choice` 的
`confidence` 当成 `probability` 会把「选项间的相对置信」与「二元肯定概率」混为一谈，
两者不是同一个量。

**与 `adapter: json` 的差别在概率性质**：systemone 走 `native`，产出的是校准
概率，按 §3.10 的「非校准概率必须标注」不适用（不标 `UNCALIBRATED`）；`json`
适配器产出的 probability 是模型自报值，必须标 `calibrated: false` 与
`UNCALIBRATED`（§4.4b）。高风险判定优先用 systemone 这样的原生实现（§7.2）。

**为什么不再写「模型在参考实现清单」**：参考实现清单（附件 E.2）是文档里的模型族
名单，配置层读不到「这个模型是不是 jev」——它只知道 `source` 与 `serves`。按
清单判 `native` 意味着解析器要维护一份模型名单并猜测用户填的路径对应谁，猜错
就把非原生模型按 `native` 调用，拿不到校准概率还丢掉 §4.4b 的 `UNCALIBRATED`
告知。改为按 `source` 判定后，规则可由配置本身判定，无需外部名单。

`native` 是**初值不是保证**：模型是否真的按槽位契约输出，由首次使用的形状校验
确定，不符则按 §3.11 降级或禁用并告警（§18.9 的「能力不符」层）。

**各协议适配器都直接归一到 §3.2 槽位形状，不经过中间协议形状**：systemone
适配器把槽位请求转成命名问题、把 `noul` 转回 `probability`；`json` 适配器把
槽位请求转成 prompt + JSON schema、把解析结果转回槽位形状。**没有「先统一转成
某个协议形状、再转回槽位形状」这一层**——统一协议形状不会让概率更准（概率性质
由后端模型决定，不由载体决定，见 §18.1 的协议选择原则），只会多一层映射、多一处
真相、多一处可能出错。

**非校准概率必须标注**：`json` 适配器产出的 probability 是模型自报值，不是校准
概率。返回的 structuredContent 带 `calibrated: false`（程序字段，与 §4.4b 的 `UNCALIBRATED` 同源），content 按 §4.4b 的
`UNCALIBRATED` 告知（slot / adapter）；高风险判定只能用 `native`，或由云端复核
（§7.2）。这是「LLM 也能做 decide」与「门控可信」之间的边界。

**三原语与槽位的完整映射（决策，不是待办）**：

| 原语 | 答案形状 | 槽位归属 |
|---|---|---|
| `noul` | 每个问题一个校准概率 | `decide`（§3.2 二元契约） |
| `choice` | 互斥选项的逐项概率分布 | `classify`（§3.10 的 choice → scores 映射） |
| `score` | 有序量表的连续位置 + 逐级分布 | **无槽位** |

`score` 不新增槽位，也不给 `decide` 契约加问题类型维度：槽位词汇表（§3.1）是
固定集合，A-4 已否决「让一个槽位承担三种问题形状」
（[architecture-review-2026-11-09-typed-decide-align.md](../architecture-review-2026-11-09-typed-decide-align.md)
第 5 节）。工具层的有序量表判定（§5.1 的 severity、§10.1 的 need_pixels）继续由
§5.1 的二元分解承接。要用 `score` 原生形状，须按 A-4 第 5.3 节的两条触发条件
重开评审；附件 E.13 的对照实测只满足其中一部分证据，不构成重开依据。

**两个典型场景**：

- 只配 jev（`serves: [classify, decide]`）：classify 与 decide 共用一个模型实例，
  省一份常驻内存（§18.1 的实例按模型文件去重）；
- 只配 LFM3-VL（`serves: [summarize, vision]`）：文本摘要与图片理解共用一份
  多模态权重，vision 不需要单独配。

### 3.11 能力声明与实际不符：校验与失效

`serves` 是**声明**，不是承诺。模型可能因为版本、量化、适配器或纯误配而不具备
声明的能力。工具层不信任声明，只信任校验。

#### 三层校验

| 层 | 做什么 | 时机 | 失败处理 |
|---|---|---|---|
| 形状校验 | 每次调用检查输出是否符合槽位契约（schema、字段、概率范围、索引覆盖） | 每次调用 | 该次降级并按 §4.4b 的 `DEGRADED` 告知 |
| 首次使用校验 | 第一次真实调用即视为校验；可配置启动探测（`slm.probe: startup`） | 首次调用 / 启动 | 标记槽位不可用，启动告警 |
| 质量抽检 | 形状通过 ≠ 判断准确；按 §15.2 抽样复核 | 运行期抽样 | 连续低质 → 降级 / 禁用 |

#### 失效状态机

```text
declared（配置声明）
  → verified（首次校验通过）
  → degraded（单次失败，按 §7.3 降级）
  → disabled（连续 N 次失败，默认 3；或形状完全不符）
改配置（移除 serves / 换模型 / 换 adapter）并重启后恢复。
```

- 状态是进程内可丢弃缓存（§22.5），不持久化；重启重新校验；
- `toolgate list` 显示每个槽位的状态（verified / degraded / disabled + 原因 + 失败计数）；
- disabled 后不再尝试，避免每次都花一次失败调用。

#### 与配置错误的分界

- 配置错误（§18.9 前三层）是「声明不合法」——启动即失败；
- 能力不符是「声明合法但实际不支持」——启动可过，运行期校验后降级 / 禁用，并给出可行动提示：

```json
{
  "code": "CAPABILITY_MISMATCH",
  "field": "models.jev.serves[1]",
  "fact": "模型 jev 声明 serves decide，但输出缺 probability 字段",
  "reason": "模型不具备该校准输出能力，或 adapter 选错",
  "next_steps": ["换 native 模型", "把 adapter 改为 json", "从 serves 移除 decide"]
}
```

#### 防误配

- 文档与示例只写「已验证的能力」，不替模型吹能力；
- `serves` 只是可服务声明，不是质量承诺——质量按 §15.2 抽检；
- 首次使用校验默认开启，不需要用户额外配置。
