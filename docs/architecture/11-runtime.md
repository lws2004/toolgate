## 11. 边界：什么归工具层

**边界决策：本地小模型归工具层，不划到调用侧。** 边界如下：

| 能力 | 归属 | 理由 |
|---|---|---|
| 工具执行 | **toolgate** | 本职 |
| 确定性治理（截断/落盘/压缩） | **toolgate** | 必须早于数据离开 |
| **本地 SLM 判定与摘要** | **toolgate** | 这是工具的一部分，不是外部服务 |
| **本地 SLM 视觉理解** | **toolgate** | 同上 |
| 置信度门控 | **toolgate** | 判定的自然延伸 |
| agent 循环 | 调用侧 | 工具层看不到目标与步数 |
| 会话存储 / 检查点 | 调用侧 | 工具层无状态（缓存不算状态，见 §22.5） |
| 上下文压缩（跨轮） | 调用侧 | 需要看整个对话 |
| 云端模型选择 | 调用侧 | toolgate 不知道对面是谁 |
| 提示词构造 | 调用侧 | 不生成 prompt |

### 11.1 为什么 SLM 默认由工具层承担

这里的「内部」是**逻辑归属**（toolgate 负责调用与结果处理），不等于**进程内**；
物理形态（embedded / http）见 §18.1。三条理由权重不同：第一条决定默认档位，
后两条说明为什么不能把这件事外包。

1. **延迟**：跨进程调用本地模型要多一次 IPC（本机回环 1-3ms）。在判定槽位
   几十毫秒的预算里这笔开销不可忽略；30B 级 agent 模型推理是秒级，IPC 可以
   忽略，所以它更适合进程外（§18.1）。
2. **数据边界**：真正的边界是「数据不出机器」，不是「不出进程」。进程外只要走
   127.0.0.1 回环，仍在本机边界内；进程内只多一层「不经内核 socket」的保证，
   不是隔离成立与否的分水岭。要跨机器就违背 §8 的隔离目标。
3. **判据**：什么时候该调模型，取决于工具的上下文（输出多长、什么类型），
   外部服务看不到。

### 11.2 仍然不归工具层的三件事

- **跨轮压缩**：需要看整个对话历史，工具层只看单次结果
- **检查点**：需要知道「任务进行到哪」，工具层无状态
- **任务规划**：需要目标，工具层没有目标

第三条说的是**工具层**不做规划。目标可以由云端给，也可以由本地 agent 接——无论哪种，
规划都发生在工具层**之外**的循环里。本地模型如果会规划，那是「本地 agent」形态：
它**消费** toolgate 的工具，而不是成为 toolgate 的一部分（§21.7）。



### 11.3 与客户端会话压缩层的分工

**决策**：
- 跨轮压缩归客户端会话层；toolgate 只做单次结果定形（§11.2）。
- 不接受「先发送、后回写」的压缩方式；已发送内容不可回写（§16.3 对策五）。
- 工具层吸收三条：机械基线优先、结构化账卡、省略必须附可执行恢复路径。
- 判定式折叠采用保守门控：缺失不等于 0，低 margin 回退机械路径。
- 降级必须可观测，静默回退视为 bug。

dsh-ledger-compact 的对照与六条借鉴见附件 E.5。

### 13.4 一个必须先解决的设计问题

**decide 槽位的调用形态与 MCP 的请求形态不匹配。**

decide 槽位的输入是「一个 state + 任意数量命名问题」，输出是「带概率的答案集合」。
这是**一次调用问多个问题**的批量形态。

而工具调用是逐个的：read 一次、bash 一次。如果每次工具调用都单独叫一次
decide 槽位，就浪费了它「一次问多个」的能力。

解法两条，取舍已按 §6.4 的实测定案（不再是待实测项）：

**方案 A：每工具单独调 decide 槽位**。简单，但每次只问 1-2 个问题，没用到批量能力。

**方案 B：请求级批处理**。在一次工具调用的处理过程中收集所有需要判定的点，
最后统一问一次 decide 槽位。复杂，但如果一个 agent turn 里有多个工具调用（PTC 场景
常见），收益明显。

**注意用词**：这里的「一次」指的是「一次 agent turn」，不是「一次 MCP 请求」。
PTC 里每次子调用仍是一个独立的 MCP 请求，工具层不做批量入口（§21.1、§21.4）。

**前提：turn 的载体**（2026-07-28 协议无状态后新增）

方案 B 要跨多个 MCP 请求聚合判定，但无状态协议没有 turn 概念。所以：

- `_meta.toolgate/turn` 是**可选**字段：`{ turn_id, seq, budget }`；
- 客户端传了，服务端才在 turn 内聚合判定；不传退化为方案 A（每工具单独调 decide 槽位）；
- 聚合状态只在 turn 内存在、可随时丢弃（§22.5）；不得跨 turn 复用，否则 §21.2 的「无隐藏状态」被破坏；
- §13.2 已列「`_meta` 解析 + 新旧协议兼容层」这一项。

**影响面限于服务端聚合类功能**：§21.7.1 的目标链路与 §18.4 的可重放由调用方持有 turn 状态，不需要服务端参与；真正需要服务端 turn 的只有本节方案 B 与 §22 的跨调用预判。

**建议已按 §6.4 的实测改判：B 的优先级上调，在阶段 1 做判定封装时留好 turn
聚合钩子，不必等到阶段 4。** 原判据是「A 的 5.7ms 本身可忽略」，那是 H100
短输入的推理口径；本机实测（§6.4）表明一次判定的真实成本由 state 长度决定。
方案 B 把同一 turn 内的多个判定合成一次 decide 槽位调用，
收益从「省几毫秒」变成「省 N 份 prefill 与 N 次固定开销」，是数量级的。
前提仍是本节已列的 `_meta.toolgate/turn` 载体：客户端不传则退化为方案 A。

**实现阶段的落点**：阶段 1 的判定封装先实现方案 A（每工具单独调 decide 槽位）作为默认路径，
并在封装里预留 turn 聚合钩子（接收 `_meta.toolgate/turn`）；跨请求聚合判定（方案 B）
随阶段 1.5 的兼容层与阶段 4 的优化落地。客户端不传 turn 字段时永远退化为方案 A，
工具层不因此产生跨请求状态（§22.5）。

**方案 B 的协议载体已经有了，不需要新协议。** 「一次调用问多个问题」的形状在协议层
已是现成的：

- **systemone 原生就是一次请求读出多个命名问题的概率**——toolgate 已实测（§18.1）：
  一次请求九问、一次前向读出全部概率，这正是 §5.1 的九问分解能一次调用问完的原因；
- **网关侧还有同构的 batch 端点**：`POST /v1/decide/batch` 入参
  `{state, questions: {qid: {type, instructions, criteria}}}`，出参 `{qid: 与单问同构的结果}`
  （来源见附件 E.10）。

所以方案 B 要做的只有一件事：**在 turn 内把多个工具的判定问题合并成一次调用**——
问题合并、结果按 qid 回填到各自的判定槽位。协议侧不新增，适配器侧不新增形状，
只有 turn 内的聚合状态。

**聚合状态的边界不变**：只在 turn 内存在、可随时丢弃（§22.5）；不得跨 turn 复用，
否则 §21.2 的「无隐藏状态」被破坏。这与本节已有的 turn 载体要求一致——方案 B
的难点从来不是协议，是 turn 内的聚合与丢弃。

**实现状态（2026-11-09）**：方案 A 已落地为默认路径（每工具单独调 decide 槽位，
一次调用问完该工具的全部问题）。方案 B 的「跨请求聚合」**未实现**，原因不是工作量，
而是收益前提不成立：

- systemone 一次请求只读**一个 state**；不同工具的输出各自是 state，无法合并成一次调用；
- 能合并的只有「同一 state 的多个问题」，而这在单次工具调用内**已经一次问完**
  （bash 九问、read 图片七问、read 文本十问、edit 六问、task 七问）；
- `_meta.toolgate/turn` 载体已解析（`compat.rs` / `understanding.rs`），留作后续
  出现「同一 state 跨请求复用」的调用形态时再接线。

**这不算违约**：本节已定「客户端不传 turn 字段则退化为方案 A」，工具层不产生跨请求
状态（§22.5）。若将来要真正落地跨请求批量，需要协议层让客户端一次带一批问题——
那会触碰 §4.0 / §21.4 的「工具层不做批量入口」，属架构变更，需另行评审。

**进度记录（2026-11-09，实现状态，非架构决策）**：

- **bash 的 decide 判定已接入工具层**——真实调用槽位（不是占位）、产出结构化事实
  （`exitCode` / `errorKind` / `severity` / `spillPath`）、走 §7.2 的门控。判定的
  落地口径（多值语义分解成 9 个二元问题、有界 state、触发条件、失败语义）见 §5.1
  的「L1 判定的落地口径」；槽位状态与 confidence 的产出规则见 §7.3。
  判定不可用时结构化字段给 `errorKind` = `"unknown"`、`severity` = `"unknown"`、
  `failedItems` = 空数组——**与「判定为无错」是两回事**（`"none"` 才是判定得出
  「没有错误」）。
- **edit 第 4 级已接 decide 槽位**——语义对齐的实际路径是
  「**机械分诊 → 判定 → 安全应用或归因报错**」：三级机械匹配都没命中时先算机械
  相似度，相似度低于阈值直接按「根本不存在」归因（不调判定）；命中候选才问
  六个二元问题（差异类型五选一 + 能否安全应用），`failure_kind` 取概率最大者，
  建议由 `failure_kind` 机械映射、位置由机械相似度给出（判定不产出自由文本、
  不产出位置）。落地口径见 §5.4 的「第 4 级的落地口径」。
  **判定的结论要驱动写操作，所以门控在 §7.2 三档之上叠了一层不可逆性约束**：
  只有 p ≥ 0.85 才允许自动写回，0.60–0.85 的低置信档一律不自动改（报错 + 归因
