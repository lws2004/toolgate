## 11. 边界：什么归工具层

**边界决策：本地小模型归工具层，不划到调用侧。** 边界如下：

| 能力 | 归属 | 理由 |
|---|---|---|
| 工具执行 | **toolgate** | 本职 |
| 确定性治理（截断/落盘/压缩） | **toolgate** | 必须早于数据离开 |
| **本地 SLM 判定与摘要** | **toolgate** | 这是工具的一部分，不是外部服务 |
| **本地 SLM 视觉理解** | **toolgate** | 同上 |
| 置信度门控 | **toolgate** | 判定的自然延伸 |
| agent 循环 | 调用侧 | 工具层看不到目标与步数 |
| 会话存储 / 检查点 | 调用侧 | 工具层无状态（缓存不算状态，见 §22.5） |
| 上下文压缩（跨轮） | 调用侧 | 需要看整个对话 |
| 云端模型选择 | 调用侧 | toolgate 不知道对面是谁 |
| 提示词构造 | 调用侧 | 不生成 prompt |

### 11.1 为什么 SLM 默认由工具层承担

这里的「内部」是**逻辑归属**（toolgate 负责调用与结果处理），不等于**进程内**；
物理形态（embedded / http）见 §18.1。三条理由权重不同：第一条决定默认档位，
后两条说明为什么不能把这件事外包。

1. **延迟**：跨进程调用本地模型要多一次 IPC（本机回环 1-3ms）。在判定槽位
   几十毫秒的预算里这笔开销不可忽略；30B 级 agent 模型推理是秒级，IPC 可以
   忽略，所以它更适合进程外（§18.1）。
2. **数据边界**：真正的边界是「数据不出机器」，不是「不出进程」。进程外只要走
   127.0.0.1 回环，仍在本机边界内；进程内只多一层「不经内核 socket」的保证，
   不是隔离成立与否的分水岭。要跨机器就违背 §8 的隔离目标。
3. **判据**：什么时候该调模型，取决于工具的上下文（输出多长、什么类型），
   外部服务看不到。

### 11.2 仍然不归工具层的三件事

- **跨轮压缩**：需要看整个对话历史，工具层只看单次结果
- **检查点**：需要知道「任务进行到哪」，工具层无状态
- **任务规划**：需要目标，工具层没有目标

第三条说的是**工具层**不做规划。目标可以由云端给，也可以由本地 agent 接——无论哪种，
规划都发生在工具层**之外**的循环里。本地模型如果会规划，那是「本地 agent」形态：
它**消费** toolgate 的工具，而不是成为 toolgate 的一部分（§21.7）。



### 11.3 与客户端会话压缩层的分工

**决策**：
- 跨轮压缩归客户端会话层；toolgate 只做单次结果定形（§11.2）。
- 不接受「先发送、后回写」的压缩方式；已发送内容不可回写（§16.3 对策五）。
- 工具层吸收三条：机械基线优先、结构化账卡、省略必须附可执行恢复路径。
- 判定式折叠采用保守门控：缺失不等于 0，低 margin 回退机械路径。
- 降级必须可观测，静默回退视为 bug。

dsh-ledger-compact 的对照与六条借鉴见附件 E.5。

### 13.4 一个必须先解决的设计问题

**d1 的调用形态与 MCP 的请求形态不匹配。**

d1 的输入是「一个 state + 任意数量命名问题」，输出是「带概率的答案集合」。
这是**一次调用问多个问题**的批量形态。

而工具调用是逐个的：read 一次、bash 一次。如果每次工具调用都单独叫一次
d1，就浪费了它「一次问多个」的能力。

解法两条，取舍已按 §6.4 的实测定案（不再是待实测项）：

**方案 A：每工具单独调 d1**。简单，但每次只问 1-2 个问题，没用到批量能力。

**方案 B：请求级批处理**。在一次工具调用的处理过程中收集所有需要判定的点，
最后统一问一次 d1。复杂，但如果一个 agent turn 里有多个工具调用（PTC 场景
常见），收益明显。

**注意用词**：这里的「一次」指的是「一次 agent turn」，不是「一次 MCP 请求」。
PTC 里每次子调用仍是一个独立的 MCP 请求，工具层不做批量入口（§21.1、§21.4）。

**前提：turn 的载体**（2026-07-28 协议无状态后新增）

方案 B 要跨多个 MCP 请求聚合判定，但无状态协议没有 turn 概念。所以：

- `_meta.toolgate/turn` 是**可选**字段：`{ turn_id, seq, budget }`；
- 客户端传了，服务端才在 turn 内聚合判定；不传退化为方案 A（每工具单独调 d1）；
- 聚合状态只在 turn 内存在、可随时丢弃（§22.5）；不得跨 turn 复用，否则 §21.2 的「无隐藏状态」被破坏；
- §13.2 已列「`_meta` 解析 + 新旧协议兼容层」这一项。

**影响面限于服务端聚合类功能**：§21.7.1 的目标链路与 §18.4 的可重放由调用方持有 turn 状态，不需要服务端参与；真正需要服务端 turn 的只有本节方案 B 与 §22 的跨调用预判。

**建议已按 §6.4 的实测改判：B 的优先级上调，在阶段 1 做判定封装时留好 turn
聚合钩子，不必等到阶段 4。** 原判据是「A 的 5.7ms 本身可忽略」，那是 H100
短输入的推理口径；本机实测（§6.4）表明一次判定的真实成本由 state 长度决定。
方案 B 把同一 turn 内的多个判定合成一次 d1 调用，
收益从「省几毫秒」变成「省 N 份 prefill 与 N 次固定开销」，是数量级的。
前提仍是本节已列的 `_meta.toolgate/turn` 载体：客户端不传则退化为方案 A。

**实现阶段的落点**：阶段 1 的判定封装先实现方案 A（每工具单独调 d1）作为默认路径，
并在封装里预留 turn 聚合钩子（接收 `_meta.toolgate/turn`）；跨请求聚合判定（方案 B）
随阶段 1.5 的兼容层与阶段 4 的优化落地。客户端不传 turn 字段时永远退化为方案 A，
工具层不因此产生跨请求状态（§22.5）。

## 14. 路线图

第一期（阶段 1–4）只覆盖 macOS（§19.7）；Windows / Linux 从阶段 6 起规划。

### 阶段 0：架构定稿（当前）

- [x] 前提修正
- [x] 分工模型与三层结构
- [x] 各工具的智能路径
- [x] 成本模型与介入判据
- [x] 最少依赖原则与依赖台账（§1.5、§19.6）
- [x] **已审阅（2026-11-07，见 docs/architecture-review-2026-11-07.md）**

### 阶段 1：SLM 接入层

- 五个槽位的客户端适配（classify / rerank / decide / summarize / vision）
- 判定封装：把「命名问题」映射到 d1 的输入格式
- 置信度门控
- 降级路径（模型不可用时静默回退到 L0）

验收：能对一段固定文本问「有错吗」，拿到带概率的答案。

**验收形态（2026-11-09 实测通过）**：`toolgate decide` 子命令 + 本机 StartLux
服务（127.0.0.1:8090，StartLux-Decision-v1.1-4B-AutoThink）端到端，走
`source: systemone` 协议（§18.1）。实测三组 noul 概率：肯定事实 0.997、
肯定错误 0.960、state 未提及 0.126——形态与 §7.2 门控同向（概率而非布尔）。

**这一条勾选记的是实现状态，不是架构决策**：§14 是路线图，「带概率的答案」这个
验收目标在 §3.2 的 decide 契约与 §7.2 的门控里已经定案，本轮没有改动任何架构
决策，只是首次有端到端实测证据。systemone 协议本身见 §18.1。

**尚未覆盖的部分**（不影响本条验收，但阶段 1 未完）：五个槽位的客户端适配只落了
decide 一条；§13.4 的 turn 聚合钩子（方案 B）随阶段 1.5 与阶段 4 落地；
`external-protocols` feature 默认关闭，默认构建下这条路径不可用（§19.6）。

同期完成错误自检三层（§1.4.5）与 `ErrorCode` 枚举——它们是纯逻辑，不依赖模型，可以先做完。

### 阶段 1.5：兼容性

- v2 首版默认 `raw`（§4.2）
- 新旧 MCP 协议兼容层：2026-07-28 无握手 + 旧版 initialize（§13.2）
- 升级指南与客户端迁移说明

验收：v1 客户端不改参数升级后，行为与 v1 一致；新客户端可用 `auto` 与 `_meta`。

### 阶段 2：单工具接入

按收益排序接入，不做并行：

1. **bash**（收益最大）→ decide 判定 + summarize 摘要
2. **read 图片**（第二）→ d1 分类 + VL 理解
3. **search**（第三）→ d1 rerank
4. **edit**（第四）→ 四级匹配 + d1 失败归因 + 改动后的事实返回（§5.7）
5. **task**（第五）→ d1 状态判断

验收：bash / read 图片 / search / task 都有 raw 与协商两条路径，且 auto 判定正确；edit 的失败归因按 §5.4 在 d1 槽位不可用时降级告知；write / edit 不产生可协商的大块内容（§4.0 是上位约束，不是放宽验收），intent 只做统一校验与 meta 标注；理解链（§4.8）先在 bash 与 read 图片落地，多步与并发行为有测试。

### 阶段 3：协商层与 intent

- intent 参数全面接入
- 结构化输出的 schema 固定
- 置信度与 slmStatus 进 meta

验收：调用方能用 intent 精确控制拿到什么。

### 阶段 4：优化

- d1 批处理（方案 B）：优先级已按 §6.4 实测上调，见 §13.4；仍需 §13.4 的 turn 载体
- L0 预热与 L1 预判（§22）
- 流式输出（暂不做：MCP progress notification 只报进度，不改变工具结果的返回形态）
- 质量阶梯标定（优先：不需要新依赖，收益确定，见 §10.2b）
- 理解链的并发调度调优（§4.8：链级并发上限与 DAG 拓扑）
- 有损 WebP（条件触发，三条判据见 §10.2b）
- 进程组管理

### 阶段 5（可选）：本地 agent 消费形态验证

- 工具在「本地 agent 消费」形态下的行为校验（§21.7）：intent=raw、事实返回、错误 nextSteps、structuredContent 稳定
- **不包含**本地 agent 自身的实现、模型部署与完成率评测——归调用方（§21.7.9）

**说明**：这是兼容性验证，不是 toolgate 的功能阶段；是否值得做取决于调用方是否采用本地 agent。

### 阶段 6（后续规划）：Windows / Linux

- 进程管理（Job Object / POSIX）、快照数据面（FICLONE / ReFS）、路径与权限（ACL / 盘符）的移植（§19.7）
- 不在第一期承诺，不预留实现
