## 6. 成本与延迟模型

### 6.1 单次调用的成本阶梯

| 层 | 模型 | 延迟 | 何时触发 |
|---|---|---|---|
| L0 | 无 | <1ms | 永远 |
| L1 | decide / rerank 槽位 | 数 ms 到数十 ms | 需要判定或排序时 |
| L2 | summarize 槽位 | 数百 ms | 需要生成文本时 |
| L3 | vision 槽位 | 约 1s | 需要看图时 |
| L4 | 云端 | 秒级 + token 费 | 需要规划/编码时 |

**这张阶梯是「单次工具调用」的路径，不是「一次任务」的路径。** 本地 agent
（§6.3）不在这条阶梯上：它每一步都要秒级推理，但一步之内不再有云端往返。

**关键：L1 是否便宜取决于输入长度，不取决于「不生成 token」。** 5.7ms 是 H100
短输入的推理口径；本机实测（§6.4）表明固定开销与输入 prefill 都不可忽略。
所以 decide 槽位默认接入的前提是 **state 有界**——先由 L0 把候选压到 ≤2K token，
再谈「每个调用都跑」。

**这个结论依赖硬件档位**：H100 上 5.7ms 可以忽略；Apple Silicon 上数十 ms 仍
可接受（MCP 往返本身几十到几百 ms）；CPU 上数百 ms 也不因延迟关闭槽位，只按 §6.4 的输入有界与 §7.1 的内容判据决定是否触发。
三档都还要叠加 §6.4 的 prefill 项，本表数字不含它。

L2 的数百 ms 就要算账了：只有当「省下的 token 值这几百 ms」时才该触发。

### 6.2 三个场景的账：必须分形态算

三形态必须分开算账：同一条压缩路径在 F1/F2/F3 下的价值不同，不能拿单一形态的
110-114 倍当通例（§21）。

三种形态：

| 形态 | 谁看工具结果 | 结果进模型上下文吗 |
|---|---|---|
| F1 直连云端 agent | 云端模型 | 进 |
| F2 PTC 云端 agent | 程序 | 不进（除非程序 return） |
| F3 本地 agent | 本地模型 | 进本地上下文，不出机器 |

**场景 A：构建失败（4200 行 / 约 42K token）**

| 形态 | 不做治理 | 做治理 | 挡住的是什么 | 倍数 |
|---|---|---|---|---|
| F1 | 42K token 进上下文 | 摘要 380 token + 指针 | 云端 token | token 比约 110 倍；成本比 114 倍（$0.126 → $0.0011） |
| F2 | 程序拿 42K 字符串，自己切、自己 parse | 程序拿 {exitCode, failedItems, spillPath}（`intent=structured` 触发 L1/L2，见 §9.2） | 程序侧解析成本与出错风险 | 不是 token 倍数 |
| F3 | 本地模型吃 42K，挤占它自己的上下文 | 截断 + 落盘，本地模型按需读 | 本地上下文预算 | 取决于模型窗口 |

F2 那一行值得说清：程序不 return 那 42K，云端 token 就是 0——**toolgate 在这里
不省 token，省的是「程序自己解析文本」这件事**。而这件事很值钱：正则写错的
概率远高于摘要模型判错的概率。所以 F2 的收益是确定性，不是成本。

**本表的数字是估算**：按 $3/Mtok、42K token、摘要 380 token 推算，未做真实账单核对。按 §15.5 标为「估算」。

**场景 B：UI 截图分析（800KB）**

| 形态 | 不做治理 | 做治理 | 挡住的是什么 |
|---|---|---|---|
| F1 | 压缩原图约 1200 token + 视觉 token | grounding 约 300 token | token 与往返次数 |
| F2 | 程序拿 base64；若 return 给云端，图照样进上下文 | 程序拿坐标 JSON | 只在「程序要坐标而非像素」时成立 |
| F3 | 本地 VL 直接看图，零 token | 同左 | **几乎为零**——本地看本地图，本来就不花钱 |

F3 这一行是必须说的：**本地编排形态下，图片压缩与理解的 token 收益是零**。
toolgate 在这里只剩两件事——让本地模型看得懂图（vision 槽位），以及格式治理。

**场景 C：小输出（200 行 ls）**

| 形态 | 结论 |
|---|---|
| F1 | 不该走本地模型：按 §6.4 实测，2K 输入光 prefill 就要 1.2 s，换 2K→400 token 不值 |
| F2 | 更不该：程序处理 200 行是零成本 |
| F3 | 本地模型自己看，工具层只做截断保护 |

**结论：只有 F1 能用「省 token」算回本**

| 形态 | 回本判据 | 这笔账的货币 |
|---|---|---|
| F1 | 月 token 费 > 部署与维护成本 | 美元 |
| F2 | 有「结果不该进上下文」或「程序必须拿到确定结构」的需求 | 事故成本 |
| F3 | 有「数据不能出机器」或「不能依赖网络」的需求 | 合规与可用性 |

toolgate 的固定成本（常驻进程、2B 模型约 2-4GB 内存、启动加载）在三种形态下
的摊薄方式不同：F1 靠省下的 token 费，F2 靠避免的事故，F3 靠本地 agent 本来
就要付的模型成本（边际接近零）。

所以「这套架构值不值」没有统一答案，要先问：**你的形态是哪种？** 是 F1 就算
token 账；是 F2 或 F3，算的不是 token，是「数据不出本地」值多少。

这也正是 §21.5 说「压缩价值缩水」的确切含义——缩的是 F2/F3 那部分，不是机制
消失了。

### 6.3 本地模型的硬件前提

| 部署 | d1 延迟 | LFM3 延迟 | 可行性 |
|---|---|---|---|
| NVIDIA H100 | 5.7ms | 数百 ms | 理想 |
| Apple Silicon（MLX） | 数十 ms | 约 1s | 可用 |
| CPU only | 数百 ms | 数秒 | 仅 d1 勉强可用 |

这决定了「默认接入 decide 槽位」的判据是 **state 有界**（§6.1），不是延迟达标；慢机型由 §18.1 的有界队列与 §7.1 的内容判据约束，不因延迟关闭 decide 槽位。

**这张表给的是延迟量级，各槽位在每档上的具体预算见 §3.1。** 两处必须一起看：
只给量级不给档位预算，筛实现时就没有可比的尺子。

**如果本地模型要承载 agentic 能力，门槛再上一个台阶**：

| 承载什么 | 典型规模 | 硬件 | 延迟量级 |
|---|---|---|---|
| 槽位（判定 / 摘要 / 视觉） | 2B | CPU 也能跑 | 数十 ms 到 1s |
| 多步工具调用（本地 agent） | 30B 级 | 单卡 24G 或 M 系列 64G | 秒级 / 一步（云端是秒级 / 一个 turn，不是一步） |

这张表说明一件事：**「本地 agent」和「本地槽位」不是同一档部署**。前者要能跑
30B，后者 2B 就够。架构不绑定用哪档，但成本模型（§6.2）要按实际部署的那档算——
用 30B 跑槽位判定是浪费，用 2B 跑 agent 循环是跑不动。

### 6.4 prefill 与输入有界化

**决策**：
- 延迟预算按「固定开销 + prefill + 生成」计算，不把单次推理数字当端到端预算。
- 超过约 2K token 的原文不整份喂槽位模型；先做确定性召回，拼成有界窗口。
- decide 类判定的成本与「状态长度 × 问题数」成正比（服务端逐问串行、不并发）：判定
  样本截到千字符级、问题集按 intent 分级，不把整份原文与全部问题一起喂（read 文本
  路径的落地口径见 §5.3）。
- 六个工具的 `tools/list` 声明（description / inputSchema / outputSchema）是每请求常驻固定开销，硬预算 ≤1.5K token（4 B/token ≈ 6000 B）；2026-11-14 本机 release 实测中文 5999 B ≈1.50K、英文 5724 B≈1.43K（六工具字段之和，含 JSON-RPC envelope 键名）。复现：`scripts/measure_tools.py`（`--lang en` 测英文，`--json` 出快照）。
- 前缀缓存未在本机验证前，不作为架构杠杆。

实测数据与拟合过程见附件 E.3。

### 6.5 槽位实测结论

**决策**：
- H100 口径的延迟预算在本机不成立；预算已按硬件档位与输入规模重标进 §3.1 三档表（附件 E.3.2）。
- rerank、vision 的延迟只作观测与选型参考，不因超预算降级或关闭；是否触发按 §9.2 的内容判据与 §7.1 的硬性不介入决定。
- 输入规模（候选数、图像 token 数、prompt token 数）写入槽位契约。

实测表见附件 E.3。

### 6.6 强模型场景的价值决策

**决策**：
- 强模型不替换全部槽位；热路径（classify / decide）仍用轻模型。
- 强模型只用于高价值、低频率的深理解任务，并走进程外共享服务（§18.1）。
- 质量提升优先走离线蒸馏，不增加运行成本。
- 云端强模型不做槽位，避免隔离价值归零。

价值分析见附件 E.4。

## 7. 介入判据：什么时候不用本地模型

这一节是防止架构变成「什么都过一遍模型」的刹车。

### 7.1 硬性不介入

| 条件 | 理由 |
|---|---|
| intent=raw | 调用方明确要原文，加工即违背契约 |
| 输出 < 500 token | 本条只跳过 L2 摘要，不额外禁止 L1；L1 是否触发由 §9.2 的 500 token 门槛决定（低于门槛不判定，由 exitCode 机械判断）。摘要是唯一受这条限制的层 |
| 需要精确计数/格式 | SLM 会数错，用确定性代码 |
| 修改代码前的读取 | 改代码必须看原文 |

### 7.2 置信度门控

decide 槽位输出带概率，所以有明确的门控规则：

```text
p ≥ 0.85          → 采用本地判定
0.60 ≤ p < 0.85   → 采用，按 §4.4b 的 LOW_CONFIDENCE 标注低置信
p < 0.60          → 同时给出本地判定与原始内容，LOW_CONFIDENCE 记 both views returned
```

这条比「小模型可信吗」的争论有用：**它把不确定性变成了可执行的分支**。

**与 §10.1 的 need_pixels 阈值是两条轴**：本节的 p 是「判定可信度」门控，
§10.1 的 0.2 / 0.8 是「是否给原图」的输出形态阈值。同一 decide 槽位输出可以同时触发
两者（p=0.75 的图片既标注 `LOW_CONFIDENCE`，又按「两种都给」处理），不构成
§10.3 禁止的第二套阈值。

**p < 0.60 时为什么不是「不采用」而是「两个都给」**：只给原始内容，云端要
从头判定一遍；两个都给，云端可以直接采用，也可以自己核对。前者是重做，
后者是复核——后者便宜。

代价是上下文里多一份内容。但当本地判定不可信时，这份代价换的是
「云端不必重新推导」。

#### 阈值只对校准概率成立

**上面那套阈值（0.85 / 0.60）是按校准概率标定的。** 校准的含义是「概率 0.9 的判定，
实际有九成是对的」——只有概率经过标定，「p ≥ 0.85 才敢采用」才成立。

但 §3.10 允许 `json` 适配器的**非校准概率**（模型自报值）进入同一个 decide 契约。
**标注了不等于可信**：§3.10 要求非校准概率带 `calibrated: false` 与
§4.4b 的 `UNCALIBRATED` 告知，但**告知是给调用方看的，门控是工具自己做的分支**——
门控不能因为「反正已经标注过了」就照用校准阈值。

口径三条：

1. **阈值只对校准概率标定**。非校准概率**不得直接套用 0.85 / 0.60** 这套阈值——
   那套数字的前提（概率经过标定）不成立；
2. **未标定协议走最保守档**：`json` 适配器产出的概率一律按「两视图都给 +
   `UNCALIBRATED` 标注」处理（fail-safe，不乐观采用），而不是按 p 值分档采用；
3. **等实测标定后再改**：某个协议在本机实测出可用的专用阈值后，再按 §15.6 的
   「判定准确率」指标（待标定）观测它，并在本机标定出专用阈值，届时才允许按档位
   采用。标定的做法可参照 §10.2b 的质量阶梯标定（§15.7 的「质量阶梯基准」条目）。

**这不是新概念**，是把 §3.10「非校准概率必须标注」这条既有规则在**门控处**的
后果写明：标注了还不够，门控也不能信它。高风险判定只能用 `native`（§3.10）或
由云端复核（§7.2），这条原本就有，现在补上它在门控上的具体落法。

**与 `UNCALIBRATED` / `LOW_CONFIDENCE` 的关系**：两者正交（§4.4b 的 code 选择
规则第 5 条）。非校准概率**总是**发 `UNCALIBRATED`；是否也发 `LOW_CONFIDENCE`
取决于走的是哪档——保守档下两者都发（概率性质 + 不确定性），校准概率在
0.60–0.85 档只发 `LOW_CONFIDENCE`。

#### 分布形状：独立于 p 的第二维门控信号

三档门控（0.85 / 0.60）只作用在**校准概率 p** 上。当判定走原生多值原语时，
`choice` 的 `confidence`（分布集中度）、`none_probability` 与 `score` 的逐级分布
/ 连续位置是**另一类量**：它们描述「结论在候选间有多集中」，不是「结论为真」的概率。

三条决策：

1. **不混合、不换算**：这些字段不得套用 0.85 / 0.60 阈值，不得与 p 取 min、加权或
   相加；把 `confidence` 当 `probability` 属 §3.10 禁止的静默转换。三档阈值与
   §7.3 的 confidence 取值口径**不变**。
2. **作为并列的 fail-safe 维度**：当工具层判定采用 `choice` / `score` 时，分布平坦
   （`confidence` 低）或 `none_probability ≥ 0.2`（官方建议阈值，附件 E.10）→ 本次
   直接按「两视图都给 + `LOW_CONFIDENCE`」处理，即使 p 仍在高档；p 低但分布集中时
   也不因此放宽 p 的门控。两个维度取**更保守**的那个。
3. **数据源约束**：当前工具层走 noul 二元分解，拿不到分布形状，本维度暂不产生分支；
   只有判定改用原生多值原语后才生效。是否改用按 A-4 的重新评估触发条件
   （[architecture-review-2026-11-09-typed-decide-align.md](../architecture-review-2026-11-09-typed-decide-align.md)
   第 5 节）决定，不预先改工具层。

**为什么写这条**：§7.3 记录的痛点是「多个独立二元概率取 min 把门控压到恒低」
（附件 E.13 的 8 条构造样本里 6/8 落 `<0.60`）。分布集中度不依赖「被选中的非答案
问题概率」，是这类判定更合适的门控输入；但它与 p 是两件事，不能互相替代。

#### 判定驱动的写操作：比只读判定更严

上面三档门控管的是**内容可信度**——「这个判定能不能拿给调用方看」。当判定的结论
要驱动**写操作**时（edit 第 4 级的归一化应用），要在三档之上**再叠一层不可逆性
约束**：

| 门控档位 | 只读判定 | 驱动写操作 |
|---|---|---|
| p ≥ 0.85 | 采用 | **允许自动写回** |
| 0.60 ≤ p < 0.85 | 采用 + 标 LOW_CONFIDENCE | **不自动改**：报错 + 归因 + 建议，把决定权交回调用方 |
| p < 0.60 | 两视图都给 | **不自动改**：同上 |

**理由是不可逆性不对称**：只读判定错了，只是结论错（调用方看到的是一段可能不准的
说明）；写操作错了，是**文件被改了**。§18.5 的写前复核（指纹比对）与 §20 的写前
快照是**兜底**，不是「可以放宽门控」的理由——它们能让你事后恢复文件，不能让一个
只有六成把握的判断去动用户的代码。

**这是在既有门控之上叠加，不是另立一套阈值。** 三档的阈值不变（0.85 / 0.60），
变的是**低置信档能否自动写回**：只读判定可以（标了 LOW_CONFIDENCE 调用方自己判断），
写操作不行——调用方要拿到的是「没改」而不是「改了但你小心点」。

**门槛作用在 §7.3 的 confidence 上**（本次被采纳结论所依赖的问题概率的最小值，
不是所有问题的最小值）。**当前模型下这条门槛在实践中偏紧**：edit 的 `format` 类
实测置信度约 0.23，远低于 0.85，所以第 4 级多数走「不写回 + 归因 + 建议」这一支。
**这是门槛在起作用，不是缺陷**——写操作本来就该谨慎；但它也说明「自动应用」这条
路需要更明确的模型或更细的分解才能达到门槛。**作为待观测项**：edit 自动应用率与
判定准确率按 §15.6 的「判定准确率」指标一起观测，达标前不放松门槛。

**不自动改时的返回形态**：按 §1.4.5 的 ToolError 三段式返回，错误里给归因
（`failure_kind`）与建议（机械映射，见 §5.4），`nextSteps` 让调用方选择：补上下文
重试 / 缩小范围 / 强制指定位置。**这与「判定不可用时的机械归因」是同一个出口**——
写操作要么确定地改，要么确定地不改并说清楚为什么。

### 7.3 降级路径

本地模型不可用时（未安装、显存不足、推理失败），工具必须仍然工作。
逐槽位的降级行为见 §3.8，这里只强调五条原则：

1. **降级对程序静默、对模型显式**：不因为本地模型挂了就让工具报错；但影响内容可信度的降级（摘要变原文、置信度低、槽位不可用）必须按 §4.4b 的 DEGRADED / LOW_CONFIDENCE / SLOT_UNAVAILABLE 写进 content 文本，不能只放 meta；
2. **降级要标注**：`meta` 的 `slmStatus` 写清哪个槽位不可用，content 按 §4.4b 的 `SLOT_UNAVAILABLE` 渲染，供模型与程序各自判断；
3. **降级后仍是可用产品**：全部槽位为空时退化为纯机械治理层（§3.8），
   解决「不丢信息、不破坏文件」两个问题，只是不解决「少传」。
4. **延迟超预算不算降级**：某槽位在本机实测超过所在档位的预算（§3.1）时，只记录到观测指标（§15.6），不触发降级、不改为「按判据触发」、也不跳过调用；是否调用按 §7.1 与 §9.2 的内容判据决定。降级只由客观失败触发（§3.11 形状不符、§18.1 调用失败或超时、§7.2 置信度、§8.7 隔离规则、§3.8 槽位不可用）。
5. **能力不符也算降级**：模型声明了 `serves` 但输出不符合槽位契约时，按 §3.11
   标记 degraded / disabled，并按 §4.4b 的 DEGRADED 告知；连续失败后禁用该槽位。

**返回契约（阶段 3 落地）**：`slmStatus` 是对象，键为六个槽位名（classify / rerank /
decide / summarize / vision / embedding），取值是封闭四态：`ready`（可用）/ `loading`（已配置、懒加载
未就绪，§18.1 第 3 条）/ `unavailable`（未配置或已卸载，§3.8）/ `degraded`（形状不符或
连续失败被禁用，§3.11）。六个槽位全空时全部为 `unavailable`。`meta.confidence` 是本次
本地判定的概率数值，**没有判定输出时为 `null`，不填 0、不省略成假值**（§4.6 诚实）。
`meta.intent` 写本次生效的五档值（§4.2）。三者由工具层在返回出口统一注入，六个工具
共用一份事实源，各工具不自行拼装。

#### 槽位状态与 confidence 的真实来源

上面四态是契约；这一段写**实现怎么产出这些值**，避免出现「契约写了、返回里却是
占位值」的落差。

**`slmStatus` 的来源**：

| 状态 | 判定依据 |
|---|---|
| `unavailable` | 该槽位**未绑定**（`models` / `slots` 里没有它能服务的模型，§3.10）；或已绑定但**当前构建不含该来源所需的协议客户端**（外部协议属可选层，默认构建关闭 `external-protocols`，§19.6）——已绑定不等于能用，不能标 `ready`；具体是哪一种见 `slmStatusDetail` |
| `ready` | 已绑定且健康（首次使用校验通过，§3.11） |
| `degraded` | 已绑定但**连续失败被禁用**，或形状校验不符（§3.11 的失效状态机） |
| `loading` | embedded 后端懒加载未就绪（§18.1 第 3 条）——**当前实现不产出这个值**，因为 embedded 后端尚未实现（§19.6 可选层） |

**`slmStatusDetail` 的来源**：`slmStatus` 只给四态，不解释「为什么不可用」；`slmStatusDetail` 是同一份判定的第二视图，键与 `slmStatus` 相同，值只在 `unavailable` / `degraded` 时出现：

```json
"slmStatusDetail": {
  "summarize": {
    "reason": "no_client",
    "nextSteps": ["当前构建未含该来源的协议客户端", "用 cargo build --release -p toolgate-cli --features external-protocols 重建"]
  }
}
```

它**不是新的状态值**：读 `slmStatus` 的调用方不受影响。两个通道（content 的 `reason=` 与这里的 `reason`）由同一份判定产出，不在两处各算一遍。

契约要求：

- `reason` 的枚举与 `SLOT_UNAVAILABLE.reason` 完全一致（`unbound` / `source_slot_mismatch` / `no_client` / `disabled` / `call_failed`，§4.4b）；
- `nextSteps` 是最少可执行的下一步，不是文案：每条一句，按顺序尝试；
- 槽位在 `ready` / `loading` 时该键不出现，不输出空对象。

这是 §1.4.5 第三层「可执行下一步」在告知通道上的延伸：告知不是错误，但同样要能让调用方知道该改配置还是重编译。

**`meta.confidence` 的来源**：本次 L1 判定输出的概率。

**confidence = 本次被采纳结论所依赖的问题概率的最小值**——不是「所有问题的最小
值」。具体到各工具：

| 工具 | confidence 取值 |
|---|---|
| bash | min(`has_error` 的概率, 被选中的 kind 类别概率)；判定为「无错」时取 `has_error` 概率本身 |
| edit | min(被选中的 `failure_kind` 概率, `fixable` 概率) |
| task | min(被选中的 `state` 类别概率, 被选中的 `progress` 类别概率) |
| read 图片 | auto 取 `need_pixels` 概率；structured / summary 取被选中的 `image_kind` 类别概率 |

**为什么不是「所有问题的最小值」**：多选问题的**非答案概率天然极低**——非答案本来
就该是低概率（问「是不是格式差异」而答案不是它，概率就该接近 0）。用「全部问题
的最小值」当置信度，等于把任何多问题判定都压到低置信档：实测 edit 场景里
`format` 问只有 0.0096、`file_changed` 问 0.5191，取最小值得 0.01，直接掉到
「两视图都给」档——**§7.2 的三档门控在这些工具上形同虚设，判定等于没被采用，
却白付一次模型调用的延迟**（bash 侧实测 confidence 恒为 0.05–0.07，门控恒为
both views）。

**置信度该衡量「这条结论有多可信」，不是「所有问题都多确定」。** 被采纳的结论只
依赖那几个问题（选中的类别 + 能否应用），其余问题的低概率是「它们不是答案」的
正常表达，不该拖累这条结论的可信度。**没有判定输出时为 `null`**（判定不可用、
intent=raw 未触发、或未达到 500 token 门槛）。

**实现状态的修正说明**：此前 `meta.slmStatus` 曾是硬编码的全 `unavailable`——字段
在、契约在，但值不是真实状态。**这是实现状态问题，不是架构变更**：契约（封闭四态、
按状态取值）从未变过，改的是实现按上表产出真实值。
