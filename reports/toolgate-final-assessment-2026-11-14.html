01机制是否成立：成立，且已在真实链路闭环

不是只看直连 /govern 的替身数据，而是看 DSH 真实工具结果进入模型上下文之前发生了什么。

  • 治理对象是 content，不是 value。PTC 内层 bash 的 value 原样返回给程序；真正进模型上下文的是 run_code 的 content 投影。适配器挂 post-execute 治理后者，实测会话 seq 4248 的 content 已变为 2000 行。
  • 嵌套跳过已生效。createPostHandler 在记录读指纹后判断 exec.parent !== undefined，嵌套调用直接 downstream；内层 3000 行耗时从 10.7s 降到 38ms。
  • 降级链已接通。local → delegated → L0 三档；policy.slmPrefer 可切 auto / local / delegate；本地槽位缺失时同一二进制仍以 L0 跑通。
  • 错误保真。任何路径都不改写错误原文；fact / reason / nextSteps 只进 structuredContent.error，不再追加 [SLOT_UNAVAILABLE] 文本。
架构对应：§3.8 的「本地 SLM → 反向委派 → L0」、§4.0a 的按返回形状分派、§4.2 的 intent 默认 raw、§22.5 的无会话状态，均已在代码里有落点。适配器仍只走 govern / pre，没有变成第二个编排器。
验证命令：cargo test --workspace 524 passed；--features external-protocols 517 passed；cargo clippy --workspace --all-targets 无问题；适配器 bun run test 31 passed。

05作用评估：四个象限

高收益 / 可接受成本

  • 长文本（约 8–32KB）：本地摘要 0.7% 输出、1–2s 级延迟，是当前唯一稳定的正收益场景。
  • 需要语义排序的多文档候选：rerank 有价值，但应限制候选规模（服务端 1000 docs 上限）。

高收益 / 高成本

  • 超大长文（180KB 级）：压缩比极高，但 17.4s；只有用户明确要摘要、且愿意等时才值得。
  • 3000 行同质列表：33.6% 字节换 19.4s，单位时间收益低；若只需截断，确定性问题毫秒级可解。

低收益 / 高成本

  • 60 行列表：4,950B 进、4,950B 出，453.6ms 白花；这是「为了治理而治理」。
  • 短错误：分类命中但正文保真，0% 压缩，301.5ms 只买到结构化归因，且模型看不到 structuredContent。

低收益 / 低成本

  • 结构化 JSON：按设计只补 meta/data，不压正文，≈1ms，不构成负担。
  • PTC 嵌套结果：直接跳过，38ms，不构成负担；这是本轮最有价值的工程修正。

06建议：先把「按形状 + 预算」做出来，再谈扩展

优先级按「收益确定性 / 实现成本 / 风险」排序。P0 是让现有能力不伤人的门槛；P1 是补齐体验；P2 是明确不做的事。

P0

列表治理加 2s 预算，超时走确定性兜底

调用 rerank 前先按行数 / 字节估算；超过预算就直接头尾采样 + max_lines 截断，不再请求模型。语义排序只在「搜索结果 / 多文档候选」这类确实需要顺序的场景开启，并限制候选 ≤1000。

依据：3000 行 34,893B → 23,173B 用了 19.36s；60 行 4,950B 零压缩仍花 453.6ms。确定性截断可在毫秒级得到同样的 2000 行上限，代价只是行序不语义化。

P0

长文先截断再摘要，并给显式预算

当前 183.7KB 先保留尾部 50KB 再摘要，仍要 17.4s。建议对 >64KB 的输入先做「头部 + 尾部 + 关键行（错误 / 路径 / 数字）」采样到 16–32KB，再送本地摘要；只有用户明确要完整摘要时才放宽到 120s。

依据：28.8KB 热态 1.1–1.4s；183.7KB 17.4s；冷启曾 23.5s，116KB 曾 30s 超时降 L0。延迟主要随输入增长，不先减输入，调超时只是把等待拉长。

P0

加最小可观测性：形状、槽位、耗时、字节、降级原因

daemon 目前没有按请求的 counters，无法回答「真实会话里到底命中了多少次、降级了多少次、平均省了多少字节」。建议在 /health 或 /stats 暴露聚合计数，并在日志里按 shape 打一行结构化记录。

依据：本报告只能证明单样本 ROI，不能证明日常命中率。没有这个数，就无法判断默认开启是否值得，也无法给 P1 的预算定阈值。

P1

适配器按形状/大小给不同超时，而不是全局 30s

默认短结果 5s、列表 2s、长文 30s；只有显式 summary intent 才允许 120s。超时一律 failOpen 并带一条短告知，不让一次工具调用无声卡满 30s。

依据：当前适配器 timeoutMs=30000，3000 行实测 19.36s；全局超时会把列表和长文绑在同一等待上限，无法区分「值得等」与「不该等」。

P1

错误：短文本保持逐字原文，长文本只做确定性压缩

短错误继续 100% 保真；只有错误原文超过 32KB 时，才保留首尾 + 关键行并明确标注截断，不走模型。结构化归因保留在 structuredContent，是否上屏由调用方决定，而不是默认改写正文。

依据：2,335B 错误分类命中但 0% 压缩、301.5ms；模型看到的仍是原文。错误处理器的价值在「不恶化 + 可归因」，不应为了压缩而破坏原文。

P2

暂不扩展：vision 本地、decide、embedding 不急着接

vision 本地未接，当前走 L0/元信息档；decide / embedding 本来就不在 govern 链。没有真实流量前，不要为了「槽位齐全」而接。

依据：红线 #3 要求槽位是增强不是依赖；本轮 6 槽位里真正进链的只有 summarize / rerank / classify，已足够覆盖长文、列表、错误三类。

P2

保留 PTC 嵌套跳过，并写进契约

嵌套工具结果不请求 /govern，只治理模型可见的 content；这条行为要写进适配器 README 与实现状态，避免后来者把它当 bug「修掉」。

依据：内层 38ms vs 10.7s；双层治理会让一次调用约 30s，且内层 value 本来就不进模型上下文。

07边界与风险

  • 冷启是真实风险。本地 summarize 首次 23.5s；预热已缓解，但进程重启后的首个大请求仍可能触发长等待。
  • 长文有硬上限。183.7KB 样本 17.4s；116KB 曾 30s 超时降 L0。超大输入必须先减输入，不能只调超时。
  • rerank 服务端限 1000 docs。3000 docs 返回 HTTP 400；1000 docs 约 11.3–13.6s，top_n 不降耗时。
  • 错误治理不省字节。短错误保真后 100%；这是有意的正确性选择，不是压缩能力。
  • 结构化 JSON 不压缩。按设计只补 meta/data；不要指望它在上下文瘦身上有收益。
  • 本报告是单机单次实测。不是吞吐基准，也不是多用户并发结论；平台范围仍为 macOS 第一期。
