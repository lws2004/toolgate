3 · 关键架构事实：daemon 的 govern 不用本地 SLM

crates/toolgate-daemon/src/lib.rs 的 ServerCtx 只有 { spill, cwd }，route 里 POST /govern → govern_with(&req, &ctx.spill, Some(&HttpDelegate))——只把反向委派客户端交给 core，不注入任何本地 SlotClient。所以：

  • daemon 治理链的长文/错误/列表只能靠宿主会话模型委派；本地 6 槽位只服务 toolgate serve（MCP）/list/call 工具与 CLI 调试子命令。
  • 推论：宿主不提供 delegate 端点时（纯 CLI、未挂适配器），govern 只剩机械 L0——质量见上表（截断/膨胀）。

4 · 测试发现的缺陷（待修，未擅自改动）

缺陷 A（严重）：Rust 标准编译错误不被识别

looks_like_error（govern.rs:816）只认行首 error: / traceback / panicked at / exit code 等，不认 error[E0308]: 这种带 [CODE] 的 rustc 标准错误。而这是 Rust 编译失败最高频的形态。

同内容改开头即被治理：
开头 "error: could not compile ..." → shape=error，三段式 367B/207B ✅
开头 "error[E0308]: mismatched types" → shape=pass_through，145B 原样透传 ❌

影响：真实 cargo build/cargo test 失败输出大概率整段进上下文，不治理。

缺陷 B：govern 与本地 SLM 解耦，无委派时质量骤降

见 §3。本地 lfm25 明明能在 433ms 内摘要（实测），但 daemon govern 链用不上它——长文只能硬截断到 50KB、错误只能套机械模板（还膨胀）。

注：这是架构取舍（§18.7 委派给宿主），不是 bug；但意味着「配好本地模型」对 daemon govern 无增益，需向使用者讲清。

缺陷 C：L0 机械治理的兜底质量不佳

长文 truncate_tail 只保留末尾 50KB/2000 行（丢失前部 37%，非摘要、不可读）；错误模板 error_view_from_text 产出「事实/原因/可选下一步」固定句式，对具体错误无信息增益，还会让字节膨胀（267→367B，137%）。

缺陷 D：委派若用弱模型，摘要质量不可靠

本测试用 lfm25(1.2B) 作委派替身，2500 行文件清单被摘要成「27 篇文本、不超过 80MB」等明显事实错误。说明委派质量强依赖宿主模型强度——生产中回投宿主强模型是对的，但不应改用本地小模型做委派。
